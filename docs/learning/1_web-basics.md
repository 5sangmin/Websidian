# Web Basics

## Purpose

이 문서는 Websidian을 구현하기 전에 알아두면 좋은 웹의 가장 기초적인 개념을 정리한다.

설명 방식은 가능한 한 다음 흐름을 따른다.

- 기존에는 무엇이 문제였는가
- 그 문제를 해결하기 위해 어떤 개념이 등장했는가
- 그 개념은 실제로 무엇을 해결하는가
- Websidian에서는 이 개념이 어디에 연결되는가

이 문서는 설계의 공식 기준 문서가 아니라 학습 문서다. 실제 구조 결정은 `docs/architecture`, `docs/backend`, `docs/frontend`, `docs/database`, `docs/infra` 문서를 따른다. 

## 1. 웹이란 무엇인가

웹은 브라우저와 서버가 네트워크를 통해 문서와 데이터를 주고받는 시스템이다. 처음의 웹은 주로 정적인 문서를 연결해서 보여주는 용도였고, 문서 중심의 하이퍼텍스트 시스템에 가까웠다. 시간이 지나면서 단순 문서 열람만으로는 부족해졌고, 사용자 입력, 데이터 저장, 로그인, 검색, 파일 업로드 같은 요구가 늘어나면서 지금의 웹 애플리케이션 형태로 발전했다.

Websidian도 이 흐름 위에 있다. 겉으로 보면 “문서를 웹에서 보는 서비스”지만, 실제로는 문서 조회, 파일 저장, 메타데이터 관리, 링크 탐색, 권한 처리 같은 여러 기능이 결합된 웹 애플리케이션이다.

### 왜 웹이 중요한가

웹은 운영체제에 크게 구애받지 않고 브라우저만 있으면 접근할 수 있다는 장점이 있다. 로컬 앱처럼 설치 부담이 크지 않고, URL을 통해 문서나 화면의 진입점을 쉽게 공유할 수 있다. Websidian이 “Obsidian 스타일 문서 경험을 웹으로 확장”하려는 이유도 바로 여기에 있다.

## 2. 브라우저와 서버

### 기존 문제

초기의 관점에서 보면, 사용자는 화면을 보고 싶고 데이터는 어딘가에 저장되어 있어야 한다. 그런데 모든 데이터를 사용자 컴퓨터 안에만 두면 다른 기기에서 접근하기 어렵고, 공유와 중앙 관리도 힘들어진다.

### 등장한 개념

이 문제를 해결하기 위해 **클라이언트-서버 모델**이 널리 쓰이게 되었다. 클라이언트는 사용자와 가까운 쪽에서 화면과 입력을 담당하고, 서버는 데이터를 관리하고 요청에 응답한다.

### 핵심 개념

- **클라이언트(Client)**: 사용자가 직접 만지는 쪽. 보통 브라우저에서 실행되는 프론트엔드 앱을 뜻한다.
- **서버(Server)**: 요청을 받고, 데이터를 처리하고, 결과를 돌려주는 쪽이다.
- **브라우저(Browser)**: HTML, CSS, JavaScript를 해석해 화면을 그리는 클라이언트 프로그램이다.

### Websidian에 대입

- 브라우저: Websidian 프론트엔드(Vue 앱)를 실행한다.
- 서버: Spring Boot 백엔드가 API 요청을 처리한다.
- 데이터 저장소: PostgreSQL과 MinIO가 각각 메타데이터와 파일을 저장한다.

즉, Websidian은 “브라우저에서 화면을 보여주고, 서버가 문서 정보를 계산해서 전달하는 구조”다.

## 3. 문서에서 애플리케이션으로

### 기존 웹의 한계

초기 웹은 정적인 HTML 문서를 서버가 그대로 보내고, 브라우저는 그 문서를 보여주는 방식이 중심이었다. 이 방식은 읽기에는 좋지만, 복잡한 사용자 상호작용에는 한계가 있었다.

예를 들어 다음과 같은 요구가 생기면 더 복잡한 구조가 필요해진다.

- 문서를 수정하고 저장하기
- 검색 결과를 즉시 갱신하기
- 폴더/목록/상세 화면을 부드럽게 이동하기
- 로그인 상태에 따라 다른 화면 보여주기
- 파일 업로드 진행 상태 보여주기

### 등장한 개념

그래서 웹은 단순 문서 전달에서 **웹 애플리케이션** 방향으로 발전했다. 서버는 단순히 HTML 한 장만 보내는 것이 아니라, 데이터를 제공하는 API 서버 역할도 맡게 되었고, 브라우저 쪽 JavaScript는 더 풍부한 UI를 담당하게 되었다.

### Websidian에 대입

Websidian은 단순 블로그가 아니라 다음을 동시에 다뤄야 한다.

- Vault 목록과 상세 보기
- Markdown/HTML 문서 렌더링
- 문서 간 링크 탐색
- 파일 메타데이터 및 다운로드
- 이후 검색, 태그, 그래프, 버전 관리 확장

그래서 “브라우저 + API 서버 + DB + 객체 스토리지”라는 구조가 자연스럽다.

## 4. URL과 진입점

### 기존 문제

문서나 화면에 접근하려면 “어디로 가야 하는지”를 식별할 방법이 필요하다. 로컬 프로그램은 메뉴나 파일 경로를 사용하지만, 웹은 네트워크를 통해 자원에 접근하므로 주소 체계가 중요하다.

### 등장한 개념

이 문제를 해결하는 기본 개념이 **URL**이다. URL은 웹에서 자원에 접근하기 위한 주소다.

예를 들면:

- 페이지 주소: `/vaults/my-notes`
- API 주소: `/api/v1/vaults`
- 파일 다운로드 주소: `/api/v1/files/{fileId}/download`

### 핵심 구분

웹 개발에서는 URL이 크게 두 종류로 자주 쓰인다.

- **페이지 URL**: 사용자가 브라우저에서 들어가는 화면 주소
- **API URL**: 프론트엔드가 백엔드에 데이터를 요청하는 주소

### Websidian에 대입

- 사용자는 Vault 페이지 같은 화면 URL로 들어간다.
- 프론트엔드는 내부적으로 `/api/v1/...` API를 호출해 필요한 데이터를 가져온다.

즉, 같은 웹이라도 “사람이 보는 주소”와 “프로그램이 호출하는 주소”가 나뉜다.

## 5. HTTP: 브라우저와 서버의 대화 규칙

### 기존 문제

클라이언트와 서버가 통신하려면 서로 같은 방식으로 말해야 한다. 요청 형식이 제각각이면 브라우저와 서버는 통신할 수 없다.

### 등장한 개념

이 문제를 해결하는 공통 규칙이 **HTTP**다. HTTP는 웹에서 요청과 응답을 주고받는 프로토콜이다.

### 핵심 개념

HTTP 통신은 보통 다음처럼 생각하면 된다.

1. 클라이언트가 요청(Request)을 보낸다.
2. 서버가 요청을 처리한다.
3. 서버가 응답(Response)을 돌려준다.

요청에는 보통 다음이 들어간다.

- 메서드(Method): 무엇을 하려는가
- URL: 어디에 요청하는가
- 헤더(Header): 부가 정보
- 바디(Body): 서버에 보낼 데이터

응답에는 보통 다음이 들어간다.

- 상태 코드(Status Code): 결과가 성공인지 실패인지
- 헤더(Header): 응답 관련 정보
- 바디(Body): 실제 응답 데이터

### 자주 보는 HTTP 메서드

- `GET`: 조회
- `POST`: 생성
- `PATCH`: 일부 수정
- `PUT`: 전체 교체 성격의 수정
- `DELETE`: 삭제

### 자주 보는 상태 코드

- `200 OK`: 정상 조회/처리 성공
- `201 Created`: 생성 성공
- `204 No Content`: 성공했지만 응답 본문 없음
- `400 Bad Request`: 잘못된 요청
- `401 Unauthorized`: 인증 필요
- `403 Forbidden`: 권한 없음
- `404 Not Found`: 대상 없음
- `500 Internal Server Error`: 서버 내부 오류

### Websidian에 대입

`GET /api/v1/documents/{documentId}` 요청을 보내면, 서버는 문서 정보를 찾아서 JSON으로 돌려준다. 이것이 Websidian에서 문서를 조회하는 기본 대화 방식이다.

## 6. 프론트엔드와 백엔드

### 기존 문제

웹 기능이 늘어나면서 “화면을 그리는 코드”와 “데이터를 처리하는 코드”가 한 군데에 뒤섞이기 시작했다. 이렇게 되면 유지보수가 어려워지고, UI 변경과 데이터 처리 로직이 서로 강하게 엮인다.

### 등장한 개념

그래서 역할을 분리하는 관점이 중요해졌다.

- **프론트엔드(Frontend)**: 사용자에게 보이는 화면과 상호작용 담당
- **백엔드(Backend)**: 데이터 처리, 저장, 인증, 비즈니스 로직 담당

### 프론트엔드의 역할

- 화면 렌더링
- 사용자 입력 받기
- API 호출
- 로딩/에러/빈 상태 처리
- 라우팅과 화면 전환

### 백엔드의 역할

- 요청 검증
- 비즈니스 로직 실행
- DB/스토리지 접근
- 권한 검사
- 표준화된 응답 반환

### Websidian에 대입

- Vue 프론트엔드: Vault 페이지, 문서 뷰어, 라우팅 담당.
- Spring Boot 백엔드: Vault/Document/File API 담당.

이 분리는 이후 레이어드 아키텍처를 이해하는 기반이 된다.

## 7. 데이터와 저장

### 기존 문제

웹 애플리케이션은 화면만 있다고 끝나지 않는다. 사용자, 문서, 파일, 링크 같은 정보를 저장해야 한다. 그런데 모든 종류의 데이터를 한 저장소에 똑같이 넣는 것은 비효율적일 수 있다.

### 등장한 개념

그래서 데이터 성격에 따라 저장소를 나눈다.

- **데이터베이스(DB)**: 구조화된 메타데이터 저장
- **객체 스토리지(Object Storage)**: 파일 자체 저장

### Websidian에 대입

Websidian은 PostgreSQL과 MinIO를 함께 사용한다. 

- PostgreSQL에 저장할 것:
  - Vault 메타데이터
  - Document 메타데이터
  - File 메타데이터
  - Tag, Link, Permission, Version 같은 관계 정보 
- MinIO에 저장할 것:
  - Markdown/HTML 본문 파일
  - 이미지
  - PDF 등 바이너리 파일

즉, “무엇이 어디에 저장되는지”를 나누는 것이 웹 앱 설계의 핵심 중 하나다.

## 8. HTML, CSS, JavaScript

### 기존 문제

브라우저에 화면을 보여주려면 단순 텍스트만으로는 부족하다. 문서 구조, 디자인, 동작을 구분해서 표현할 필요가 생겼다.

### 등장한 개념

그래서 브라우저 세계에서는 세 가지 기본 언어가 자리 잡았다.

- **HTML**: 구조
- **CSS**: 스타일
- **JavaScript**: 동작

### 각각의 역할

- HTML: 제목, 문단, 링크, 버튼, 이미지 등 “무엇이 있는가”를 표현
- CSS: 색, 여백, 폰트, 레이아웃 등 “어떻게 보이는가”를 표현
- JavaScript: 클릭, 요청, 상태 변화 등 “어떻게 움직이는가”를 표현

### Websidian에 대입

Vue는 결국 HTML/CSS/JavaScript를 더 구조적으로 다루기 위한 프레임워크다. 즉, Vue를 배우는 것은 브라우저의 세 기본 언어를 더 편하게 다루는 도구를 배우는 것에 가깝다. 

## 9. 페이지, 라우팅, 상태

### 기존 문제

웹 애플리케이션이 커지면 한 화면만으로는 부족하다. 목록, 상세, 편집, 설정 같은 여러 화면이 필요하고, 각 화면은 서로 다른 데이터를 가져와야 한다.

### 등장한 개념

이 문제를 다루기 위해 다음 개념이 중요해진다.

- **페이지(Page)**: 사용자가 하나의 화면 단위로 인식하는 UI
- **라우팅(Routing)**: URL에 따라 어떤 페이지를 보여줄지 결정
- **상태(State)**: 지금 화면이 가지고 있는 데이터와 UI 상태

### 상태란 무엇인가

상태는 “지금 이 화면이 무엇을 알고 있는가”라고 생각하면 쉽다.

예:

- 현재 선택된 vault slug
- 현재 문서 데이터
- 로딩 중인지 여부
- 에러가 있는지 여부
- 검색어 입력값

### Websidian에 대입

프론트엔드 구조 문서는 페이지, 컴포넌트, 라우팅, 상태 관리를 구분해서 잡는 방향을 제시한다. 이는 앱이 커질수록 어디에 어떤 코드가 있어야 하는지 명확히 하기 위해서다. 

## 10. API가 필요한 이유

### 기존 문제

예전에는 서버가 HTML을 완성해서 통째로 내려주는 방식이 많았다. 하지만 프론트엔드가 복잡해지고, 같은 데이터를 웹 UI 외의 다른 클라이언트에서도 쓰고 싶어지면서 “데이터를 화면과 분리해 제공할 방법”이 필요해졌다.

### 등장한 개념

이때 핵심이 **API(Application Programming Interface)**다. API는 프로그램과 프로그램이 약속된 방식으로 통신하게 해주는 인터페이스다. 

웹에서의 API는 보통 다음 역할을 한다.

- 프론트엔드가 데이터 요청
- 백엔드가 JSON 응답
- 프론트엔드가 그 JSON을 이용해 화면 구성

### Websidian에 대입

Websidian API는 REST 스타일, `/api/v1` 버전 prefix, JSON 응답을 사용하는 방향으로 정리되어 있다. 

즉, API는 Websidian에서 프론트와 백엔드를 연결하는 공식 통로다.

## 11. 왜 문서를 먼저 쓰는가

### 기존 문제

기능을 바로 구현하면 처음에는 빨라 보이지만, 조금만 지나도 “왜 이렇게 만들었는지”를 잊기 쉽다.  
특히 개인 프로젝트에서는 과거의 내가 남긴 문맥이 사라지면 다시 시작하기가 어려워진다.

### 등장한 개념

그래서 Websidian은 Docs-as-Code 방향을 택했다. 구조, 범위, 결정 이유를 문서로 먼저 남기고, 구현은 그 문맥을 따라간다. 

### Websidian 문서 구조의 의미

- `docs/vision`: 왜 이 프로젝트가 존재하는가
- `docs/architecture`: 시스템을 어떤 구조로 볼 것인가
- `docs/backend`: API와 백엔드 구조는 어떤 방향인가
- `docs/frontend`: 화면 구조는 어떤 방향인가
- `docs/database`: 데이터는 어떻게 모델링하는가
- `docs/infra`, `docs/operations`: 실행과 운영은 어떻게 할 것인가 

이 구조는 “생각과 구현이 같이 움직이게 하려는 장치”다.

## 12. 왜 작은 단위로 구현하는가

### 기존 문제

개발 초기 가장 흔한 문제는 전체를 한 번에 만들려는 것이다. 그러면 개념도 많고, 연결점도 많고, 어느 층이 깨졌는지 파악하기가 어렵다.

### 등장한 개념

그래서 development guide는 큰 기능을 **작은 work unit**으로 자르고, 가능한 한 하나의 흐름을 끝까지 관통하는 **vertical slice** 방식으로 구현하라고 안내한다. 

예를 들면 이런 단위다.

- Vault 목록 조회
- Vault entry document 조회
- 문서 상세 조회
- 파일 다운로드 URL 발급

### 왜 좋은가

- 프론트-백엔드-DB가 어떻게 연결되는지 빠르게 이해할 수 있다.
- 막혔을 때 범위가 작아 디버깅이 쉽다.
- 작은 성공 경험을 반복할 수 있다.

Websidian처럼 문서 플랫폼을 만드는 경우, 이 접근이 특히 중요하다. 

## 13. Websidian에서 웹 기본 개념이 어떻게 이어지는가

아래는 지금까지 설명한 개념을 Websidian에 연결한 간단한 흐름이다.

1. 사용자가 브라우저에서 Vault 페이지 URL로 접속한다.
2. Vue 프론트엔드가 라우팅을 해석하고 필요한 API를 결정한다. 
3. 프론트엔드가 Spring Boot 백엔드에 HTTP 요청을 보낸다. 
4. 백엔드는 PostgreSQL에서 메타데이터를 조회하고, 필요하면 MinIO 경로도 함께 계산한다. 
5. 백엔드는 JSON 응답을 반환한다. 
6. 프론트엔드는 이 데이터를 상태에 저장하고 화면을 렌더링한다. 
7. 사용자는 문서를 읽고, 나중에는 링크 탐색·검색·편집·버전 기능으로 확장된 흐름을 사용하게 된다. 

이 한 줄기가 웹 개발의 전체 그림이다.

## 14. 지금 단계에서 꼭 잡아야 할 핵심 문장

아래 문장들만 정확히 이해해도 출발점으로 충분하다.

- 웹은 브라우저와 서버가 HTTP로 통신하는 시스템이다.
- 프론트엔드는 화면과 사용자 상호작용을 담당하고, 백엔드는 데이터와 규칙을 담당한다.
- API는 프론트엔드와 백엔드를 연결하는 통로다. 
- DB는 메타데이터를 저장하고, 객체 스토리지는 파일 자체를 저장한다. 
- URL, 페이지, 라우팅, 상태는 프론트엔드 앱을 이해하는 기본 단위다. 
- 문서를 먼저 읽고, 기능을 작게 잘라 구현하는 것이 Websidian의 기본 작업 방식이다.
