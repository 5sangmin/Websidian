# Engineering Concepts

## Purpose

이 문서는 앞에서 다루지 못했거나, 각 문서에 흩어져 있었던 실무적 개념들을 한 번 더 정리한다.

설명 방식은 가능한 한 다음 흐름을 따른다.

- 기존에는 무엇이 문제였는가
- 그 문제를 해결하기 위해 어떤 개념이 등장했는가
- 그 개념은 실제로 무엇을 해결하는가
- Websidian에서는 이 개념이 어디에 연결되는가

이 문서는 학습 문서다. 실제 Websidian의 구조와 구현 방향은 `docs/architecture/*`, `docs/backend/*`, `docs/frontend/*`, `docs/database/*`, `docs/infra/*`, `docs/operations/*` 문서를 기준으로 본다. 

## 1. 이 문서는...

### 기존 문제

처음 학습할 때는 보통 기술을 하나씩 나눠서 이해하게 된다.

- 웹은 웹대로
- HTTP는 HTTP대로
- DB는 DB대로
- Spring, Vue, Docker도 각각 따로

이 방식은 입문에는 좋지만, 마지막에는 새로운 문제가 생긴다.  
각 개념은 알겠는데, **서로가 어떻게 연결되는지**, 그리고 실제 구현 단계에서는 어떤 기준으로 판단해야 하는지가 잘 보이지 않게 된다.

### 등장한 개념

그래서 마지막에는 개별 기술 하나보다, **기술 사이를 연결하는 공통 개념**을 정리하는 문서가 필요해진다.

이 문서는 다음 같은 질문에 답하기 위해 존재한다.

- API와 DTO는 왜 필요한가
- validation은 어디서 해야 하는가
- 에러 처리는 왜 따로 생각해야 하는가
- 인증과 권한은 무엇이 다른가
- 캐시는 언제 필요한가
- 로그는 왜 중요한가
- 테스트는 무엇을 보장하려는가
- migration은 왜 코드만큼 중요한가

### Websidian에 대입

Websidian은 단순 CRUD 예제가 아니라, 문서/파일/링크/권한/버전/스토리지를 함께 다루는 프로젝트다.  
그래서 개별 기술 학습 뒤에는, 실제 구현에서 계속 마주칠 공통 개념들을 따로 정리해 두는 편이 훨씬 도움이 된다. 

## 2. DTO는 왜 필요한가

### 기존 문제

처음에는 API 요청/응답 데이터와 내부 도메인 객체를 같은 것으로 취급하기 쉽다.

예를 들어:

- 요청 JSON을 바로 엔티티로 받기
- 엔티티를 그대로 응답으로 반환하기
- DB 구조와 API 구조를 같게 보기

이 방식은 처음에는 빨라 보이지만, 시간이 지나면 문제가 생긴다.

- API 계약이 내부 모델에 강하게 묶인다
- 응답 구조를 바꾸기 어렵다
- 불필요한 내부 정보가 외부로 노출될 수 있다
- 프론트 요구사항 때문에 도메인 구조가 흔들린다

### 등장한 개념

이 문제를 해결하기 위해 **DTO(Data Transfer Object)** 라는 개념이 중요해졌다.

DTO는 쉽게 말하면:

- 요청을 받을 때 쓰는 구조
- 응답을 돌려줄 때 쓰는 구조

다시 말해, **외부와 대화하기 위한 데이터 형태**다.

### Websidian에 대입

Websidian에서는 `CreateDocumentRequest`, `UpdateDocumentRequest`, `DocumentResponse`, `VaultSummaryResponse` 같은 구조가 DTO에 해당한다.  
레이어드 아키텍처 관점에서 DTO는 API layer 쪽에 더 가깝고, domain model과는 역할이 다르다. 

### 왜 중요한가

DTO를 분리하면 다음 장점이 생긴다.

- API 계약과 내부 모델을 분리할 수 있다
- 프론트 요구에 맞는 응답 구조를 설계하기 쉽다
- 내부 도메인 변경이 외부 API에 덜 전파된다

## 3. Validation은 왜 중요해졌는가

### 기존 문제

서버는 외부에서 들어오는 요청을 신뢰할 수 없다.  
그런데 검증 없이 바로 처리하면 다음 문제가 생긴다.

- 제목 없는 문서 생성
- 너무 긴 slug 저장
- 잘못된 enum 값 전달
- 존재하지 않는 Vault에 문서 연결 시도

즉, 시스템이 “받아서는 안 되는 입력”까지 받아들이게 된다.

### 등장한 개념

이 문제를 해결하기 위해 **Validation(검증)** 이 중요해졌다.

검증은 크게 두 층으로 생각할 수 있다.

- **입력 검증**: 요청 형식이 맞는가
- **비즈니스 검증**: 이 요청이 현재 규칙상 허용되는가

### Websidian에 대입

예를 들면:

- 요청 DTO에서 `title` 이 비어 있지 않은지 검사
- `documentType` 이 허용된 값인지 검사
- 같은 Vault 안에서 slug 중복이 없는지 검사
- entry document 로 지정하려는 문서가 실제로 그 Vault 소속인지 검사

이 중 일부는 API layer 에 가깝고, 일부는 application/domain 규칙에 가깝다. 

### 왜 중요한가

validation은 단순 에러 방지가 아니라, **시스템 경계를 지키는 첫 번째 장치**다.

## 4. 에러 처리(Error Handling)는 왜 따로 생각해야 하는가

### 기존 문제

처음에는 에러가 발생하면 그냥 예외를 던지고 끝내기 쉽다.  
하지만 시스템이 커지면 “실패도 하나의 중요한 결과”가 된다.

예를 들어:

- 문서가 없을 수 있다
- 권한이 없을 수 있다
- 파일이 MinIO에 없을 수 있다
- DB 연결이 실패할 수 있다

이런 실패를 모두 제각각 처리하면, 프론트엔드도 대응하기 어려워진다.

### 등장한 개념

그래서 **일관된 에러 처리 방식**이 중요해졌다.

보통 다음을 함께 생각한다.

- 어떤 예외를 어떤 계층에서 발생시킬지
- 어떤 HTTP 상태 코드로 바꿀지
- 응답 body를 어떤 형식으로 줄지
- 로그에는 무엇을 남길지

### Websidian에 대입

예:

- 대상 없음 → `404 Not Found`
- 잘못된 입력 → `400 Bad Request`
- 충돌 → `409 Conflict`
- 권한 없음 → `403 Forbidden`

이런 기본 규칙은 HTTP/REST 문서와도 연결되고, 실제 구현에서는 Spring의 global exception handling 구조로 이어진다. 

### 왜 중요한가

에러 처리가 정리되어 있으면:

- 프론트엔드가 예측 가능하게 대응할 수 있고
- 로그 분석이 쉬워지고
- 실패 상황도 구조적으로 관리할 수 있다

## 5. 인증(Authentication)과 권한(Authorization)은 왜 구분해야 하는가

### 기존 문제

초기 개발에서는 “로그인했는가?”와 “이 작업을 해도 되는가?”를 같은 문제로 생각하기 쉽다.  
하지만 이 둘은 실제로 다른 질문이다.

### 등장한 개념

그래서 보안에서는 두 개념을 구분한다.

- **인증(Authentication)**: 너는 누구인가
- **권한(Authorization)**: 너는 무엇을 할 수 있는가

### Websidian에 대입

Websidian에서는 앞으로 다음 구분이 중요해질 수 있다.

- 사용자가 로그인했는가
- 이 사용자가 특정 Vault를 볼 수 있는가
- 이 사용자가 문서를 수정할 수 있는가
- 이 사용자가 파일을 업로드/삭제할 수 있는가

즉, 로그인만 되어 있다고 해서 모든 작업이 허용되는 것은 아니다.

### 왜 중요한가

이 구분이 있어야:

- 공개 Vault / 비공개 Vault 정책
- 읽기 전용 / 편집 가능 권한
- 관리자 기능 접근 제어

같은 구조를 깔끔하게 설계할 수 있다.

## 6. 캐시(Cache)는 왜 등장했는가

### 기존 문제

모든 요청마다 항상 DB와 스토리지를 직접 조회하면 구조는 단순하지만, 반복 요청이 많아질수록 비효율이 커질 수 있다.

예를 들어:

- 자주 조회되는 Vault 메타데이터
- 자주 읽는 문서 본문
- 거의 바뀌지 않는 공개 문서 목록

매번 동일하게 계산하면 응답 속도와 비용 모두 손해가 생긴다.

### 등장한 개념

이 문제를 해결하기 위해 **캐시(Cache)** 라는 개념이 중요해졌다.

캐시는 “다시 계산하거나 다시 읽기 전에, 이미 있는 결과를 잠시 재사용하는 방식”이다.

### Websidian에 대입

초기 MVP에서는 캐시가 필수는 아닐 수 있다.  
하지만 나중에는 다음이 캐시 후보가 될 수 있다.

- 공개 Vault 목록
- entry document 메타데이터
- 문서 렌더링 결과
- 자주 조회되는 링크 요약

### 왜 중요한가

캐시는 성능을 높일 수 있지만, 동시에 **최신성과 복잡도**라는 비용도 만든다.  
즉, 캐시는 빠르게 만들기 위한 도구가 아니라, 필요할 때만 신중히 도입해야 하는 최적화다.

## 7. 로그(Logging)는 왜 중요한가

### 기존 문제

애플리케이션이 실패했을 때, 코드만 보고 원인을 알 수 없는 경우가 많다.  
특히 backend, DB, MinIO, frontend가 같이 움직이는 시스템에서는 어디에서 문제가 났는지 파악하기 어렵다.

### 등장한 개념

그래서 **로그(Logging)** 가 중요해졌다. 로그는 시스템이 실행 중에 남기는 기록이다.

예를 들어 로그는 다음을 도와준다.

- 어떤 요청이 들어왔는지
- 어떤 에러가 발생했는지
- 어떤 외부 시스템 호출이 실패했는지
- 애플리케이션이 어디까지 실행됐는지

### Websidian에 대입

Websidian 개발 환경 문서도 frontend, backend, postgres, minio 로그를 각각 확인하는 흐름을 중요하게 본다. 

특히 다음 상황에서 로그가 중요하다.

- Compose 환경에서 서비스 연결 실패
- MinIO endpoint 설정 오류
- DB migration 실패
- API 예외 발생

### 왜 중요한가

로그는 “문제가 생겼을 때 보는 것”이 아니라, **시스템의 현재 상태를 관찰하는 창**이다.

## 8. 테스트(Test)는 왜 필요한가

### 기존 문제

혼자 개발하는 프로젝트에서는 테스트를 나중으로 미루기 쉽다.  
하지만 기능이 쌓이면 과거에 되던 것이 지금도 되는지 확신하기 어려워진다.

특히 다음 상황에서 불안이 커진다.

- 리팩터링 후 문서 조회가 여전히 되는가
- slug 중복 검사 규칙이 유지되는가
- entry document 설정 로직이 깨지지 않았는가

### 등장한 개념

그래서 **테스트(Test)** 가 중요해졌다. 테스트는 단순히 버그를 찾는 도구가 아니라, “이 동작은 유지되어야 한다”는 사실을 코드로 기록하는 방식이다.

### Websidian에 대입

초기에는 모든 것을 다 테스트하려 하기보다, 다음부터 시작하는 편이 현실적이다.

- application service 단위 테스트
- repository 기본 조회 테스트
- 핵심 API 엔드포인트 통합 테스트

### 왜 중요한가

테스트는 solo 프로젝트에서 특히 중요하다.  
미래의 내가 과거의 코드를 바꾸면서도 덜 불안하게 만들어 주기 때문이다. 

## 9. Migration은 왜 중요한가

### 기존 문제

DB 스키마는 프로젝트 초기에 한 번 정하고 끝나는 것이 아니다.  
기능이 늘어나면 테이블, 컬럼, 인덱스, 제약조건이 바뀌게 된다.

이런 변경을 수동 SQL로만 관리하면 곧 문제가 생긴다.

- 어느 환경에 어떤 변경이 적용됐는지 헷갈린다
- 개발/테스트/운영 DB 상태가 어긋난다
- 예전 상태를 추적하기 어렵다

### 등장한 개념

이 문제를 해결하기 위해 **Database Migration** 이 중요해졌다.

Migration은 DB 구조 변경을 코드처럼 버전 관리하는 방식이다.

### Websidian에 대입

Websidian의 schema 문서와 development guide 흐름상, 스키마 초안은 문서로 먼저 잡되 실제 변경은 migration 파일로 남기는 방향이 자연스럽다. 
### 왜 중요한가

migration이 중요하다는 것은, DB도 결국 코드처럼 **변경 이력과 재현성**이 필요하다는 뜻이다.

## 10. 비동기(Async)는 왜 자주 언급되는가

### 기존 문제

웹 애플리케이션은 느릴 수 있는 작업을 자주 다룬다.

- 네트워크 요청
- 파일 업로드
- 외부 스토리지 접근
- 대용량 문서 처리

이런 작업을 모두 즉시 끝나는 것처럼 생각하면, 실제 UI와 서버 동작을 잘못 설계하기 쉽다.

### 등장한 개념

그래서 **비동기(Asynchronous)** 처리 개념이 중요해졌다.

핵심 생각은 단순하다.

- 어떤 작업은 바로 끝나지 않는다
- 그동안 기다림, 진행 상태, 실패 가능성을 고려해야 한다

### Websidian에 대입

프론트엔드에서는:

- API 로딩 상태
- 파일 업로드 진행
- 에러 재시도

같은 형태로 나타난다.

백엔드에서는:

- 외부 저장소 접근
- 긴 처리 시간
- 나중에 작업 분리 필요성

같은 문제로 이어질 수 있다.

### 왜 중요한가

비동기를 이해해야 “왜 로딩 UI가 필요한가”, “왜 타임아웃이 생기는가”, “왜 업로드와 저장을 분리해서 생각해야 하는가”를 이해할 수 있다.

## 11. idempotency와 중복 요청 문제는 왜 중요해지는가

### 기존 문제

현실의 네트워크 환경에서는 사용자가 버튼을 두 번 누르거나, 브라우저가 재시도하거나, 프론트엔드 코드가 같은 요청을 중복 전송할 수 있다.

이때 서버가 아무 대비 없이 처리하면 다음 문제가 생긴다.

- 문서가 두 번 생성됨
- 같은 파일 메타데이터가 중복 저장됨
- 상태 전환이 꼬임

### 등장한 개념

이 문제를 줄이기 위해 **멱등성(idempotency)** 같은 개념이 중요해졌다.

멱등성은 같은 요청을 여러 번 보내도 결과가 의도치 않게 달라지지 않도록 하는 성질이다.

### Websidian에 대입

초기에는 모든 API에 완전한 멱등성을 요구할 필요는 없지만, 다음 같은 작업에서는 신경 쓸 가치가 있다.

- 파일 업로드 완료 처리
- entry document 설정
- publish 같은 상태 전환
- 문서 생성 중복 방지

### 왜 중요한가

이 개념은 단순한 이론이 아니라, 실전에서 “왜 중복 클릭 때문에 데이터가 꼬였지?”를 막아 주는 관점이다.

## 12. 계약(Contract)은 왜 중요한가

### 기존 문제

프론트엔드와 백엔드가 나뉘면, 두 쪽이 같은 기능을 다르게 이해할 위험이 생긴다.

예를 들어:

- 응답 필드 이름이 다르다
- 에러 형식이 다르다
- 어떤 상태 코드를 쓸지 합의가 없다

이러면 기능은 있어도 연결이 자주 깨진다.

### 등장한 개념

그래서 **API 계약(Contract)** 이 중요해졌다.

계약이란 쉽게 말하면:

- 어떤 요청을 보내고
- 어떤 응답을 받고
- 실패 시 어떤 형식을 받는지

를 미리 정하는 것이다.

### Websidian에 대입

Websidian의 `api-overview.md` 문서는 이런 계약을 정리하는 출발점이다.  
즉, API 문서는 단순 설명서가 아니라, 프론트엔드와 백엔드가 공유하는 약속이다. 

### 왜 중요한가

계약이 분명하면:

- 프론트/백엔드 작업을 분리하기 쉽고
- 구현 중 충돌이 줄고
- 나중에 문서를 다시 읽었을 때도 빠르게 맥락을 회복할 수 있다

## 13. 구현보다 운영이 어려워지는 순간은 언제인가

### 기존 문제

초기에는 기능 구현 자체가 가장 큰 일처럼 보인다.  
하지만 시스템이 조금만 커져도 문제의 중심은 점점 달라진다.

- 어떻게 다시 띄우지
- 데이터는 어떻게 보존하지
- 환경 변수는 어디서 관리하지
- 장애가 나면 어디부터 보지
- 초기화는 어떻게 하지

즉, 코드만 있다고 시스템이 되는 것은 아니다.

### 등장한 개념

그래서 개발 후반으로 갈수록 **운영 관점**이 중요해진다.

- 실행 절차
- 백업/복구
- 로그 확인
- 재시작 정책
- 데이터 초기화 정책

같은 것이 필요해진다.

### Websidian에 대입

Websidian 문서 구조에 `docs/operations/` 와 `docs/infra/` 가 따로 있는 이유가 바로 여기에 있다.  
프로젝트를 오래 유지하려면 구현 코드뿐 아니라, **다시 실행하고 다시 회복하는 문맥**도 함께 남겨야 하기 때문이다. [file:5][file:9]

## 14. 지금 단계에서 가장 중요한 관점은 무엇인가

### 기존 문제

여기까지 읽고 나면 오히려 더 막막해질 수 있다.  
알아야 할 개념이 너무 많아 보이기 때문이다.

### 등장한 관점

하지만 실제로는 모든 개념을 한 번에 다 쓰지 않는다. 중요한 것은 **모든 개념을 외우는 것**이 아니라, **지금 필요한 만큼 연결해서 쓰는 능력**이다.

예를 들면 지금 구현 단위가 “Vault entry document 조회”라면 실제로 필요한 것은:

- HTTP GET 요청 이해
- Spring controller / service / repository 흐름 이해
- Vue 페이지 / composable / 상태 이해
- PostgreSQL 조회 이해
- 필요 시 MinIO 경로 개념 이해
- Docker로 postgres/minio 띄우기 이해

정도다.

### Websidian에 대입

development guide도 바로 이런 식의 접근을 권장한다.  
큰 주제를 한 번에 구현하지 말고, 작은 vertical slice 로 자른 뒤 필요한 개념만 연결해서 써야 한다. 

### 왜 중요한가

이 관점을 잡으면, 개념이 많아도 덜 압도된다.  
학습은 넓게 했더라도, 구현은 항상 작게 시작할 수 있기 때문이다.

## 15. 지금 단계에서 꼭 잡아야 할 핵심 문장

아래 문장들만 정확히 이해해도 마지막 정리는 충분하다.

- DTO는 외부와 대화하기 위한 데이터 구조이고, domain model과는 역할이 다르다.
- validation은 시스템 경계에서 잘못된 입력을 막는 장치다.
- 에러 처리와 상태 코드는 실패를 구조적으로 다루기 위한 규칙이다.
- 인증은 “누구인가”, 권한은 “무엇을 할 수 있는가”를 다룬다.
- 캐시, 로그, 테스트, migration은 프로젝트가 커질수록 더 중요해지는 운영적/실무적 개념이다.
- 프론트엔드와 백엔드가 분리된 구조에서는 API 계약과 일관된 응답 형식이 특히 중요하다.
- 모든 개념을 한 번에 구현할 필요는 없고, 지금 필요한 vertical slice 에 맞게 연결해서 쓰면 된다. 

## 16. 여기까지 읽었다면

여기까지 왔다는 것은 단순히 문서를 몇 개 읽은 것이 아니다.

- 웹의 기본 흐름을 이해했고
- HTTP와 REST의 대화 방식을 이해했고
- 레이어드 아키텍처의 책임 분리를 이해했고
- DB와 스토리지의 차이를 이해했고
- Spring, Vue, Docker가 각각 어디에서 어떤 역할을 맡는지 이해한 것이다

즉, 이제는 “아예 모르는 상태”가 아니라, **작게 구현을 시작할 수 있는 상태**에 도달한 것이다.

고생했다. 여기까지 읽고 정리했다는 것만으로도, 이미 대부분의 초반 혼란 구간을 통과한 것이다. 이제부터는 완벽하게 이해한 뒤 시작하려 하기보다, 작은 기능 하나를 끝까지 구현하면서 문서와 코드를 연결해 나가면 된다.

## 17. 다음 문서로 이어지는 연결

이 문서는 학습 문서 묶음의 마지막 정리 문서다.

이 다음부터는 새로운 학습 문서를 계속 늘리기보다, 아래처럼 실제 설계/구현 문서와 연결하는 것이 더 중요하다.

- `docs/backend/api-overview.md` 를 읽고 첫 API 하나 고르기
- `docs/frontend/app-structure.md` 를 기준으로 첫 페이지 하나 만들기

- `docs/operations/development-guide.md` 를 따라 작업 단위를 vertical slice 로 자르기 

즉, 다음 단계는 “더 많은 개념 읽기”보다, **작은 기능 하나를 실제로 구현해 보는 것**이다.
