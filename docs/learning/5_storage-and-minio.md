# Storage and MinIO

## Purpose

이 문서는 Websidian을 구현하기 전에 알아두면 좋은 저장소(Storage)와 객체 스토리지(Object Storage), 그리고 MinIO의 기본 개념을 정리한다.

설명 방식은 가능한 한 다음 흐름을 따른다.

- 기존에는 무엇이 문제였는가
- 그 문제를 해결하기 위해 어떤 개념이 등장했는가
- 그 개념은 실제로 무엇을 해결하는가
- Websidian에서는 이 개념이 어디에 연결되는가

이 문서는 학습 문서다. 실제 Websidian의 저장 구조 방향은 `docs/architecture/system-context.md`, `docs/database/schema-draft.md`, `docs/architecture/domain-model.md`, `docs/infra/env-vars.md` 문서를 기준으로 본다. [1][2][3][4]

## 1. 왜 저장소를 따로 생각해야 하는가

### 기존 문제

웹 애플리케이션을 처음 만들 때는 데이터 저장을 거의 전부 데이터베이스 문제로만 생각하기 쉽다. 하지만 실제 시스템은 숫자와 문자열만 저장하지 않는다.

문서 플랫폼이라면 아래 같은 대상도 저장해야 한다.

- Markdown 원문
- HTML 원본
- 이미지
- PDF
- 첨부 파일
- 렌더링에 필요한 자산 파일

이런 파일은 크기가 크고 형식도 다양하며, 조회 패턴도 일반 테이블 데이터와 다르다.

### 등장한 개념

그래서 시스템에서는 보통 **구조적 메타데이터 저장소** 와 **파일 원본 저장소** 를 구분한다. 간단히 말하면, “관계를 잘 다루는 저장소”와 “파일을 잘 보관하는 저장소”를 나눠 쓰는 것이다.

### Websidian에 대입

Websidian도 바로 이 구조를 전제로 한다. 문서, 링크, 버전, 파일 메타데이터 같은 구조적 정보는 PostgreSQL에 두고, 실제 파일 원본은 MinIO 같은 S3 호환 객체 스토리지에 둔다. 

## 2. 왜 DB에 파일을 다 넣지 않는가

### 기존 문제

처음에는 “DB 하나에 다 넣으면 단순하지 않을까?”라는 생각이 자연스럽다. 실제로 작은 프로젝트에서는 바이너리 데이터를 DB에 직접 저장하는 경우도 있다.

하지만 파일 수와 크기가 커질수록 문제가 생긴다.

- DB 용량이 빠르게 커진다
- 백업과 복구가 무거워진다
- 메타데이터 조회와 파일 원본 보관이 같은 시스템에 얽힌다
- 큰 파일 전송이 DB의 주 역할을 방해할 수 있다

즉, DB는 데이터를 잘 다루지만, 대용량 파일 원본을 오래 보관하고 안정적으로 서빙하는 데 최적화된 도구는 아니다.

### 등장한 개념

그래서 **메타데이터는 DB**, **바이너리 원본은 별도 저장소** 로 분리하는 설계가 널리 쓰이게 되었다.

### Websidian에 대입

Websidian의 `files` 테이블에는 `object_key`, `original_name`, `mime_type`, `size_bytes`, `checksum` 같은 메타데이터만 저장하고, 실제 파일 원본은 MinIO에 둔다. 

이 구조는 DB와 파일 저장소가 각자 잘하는 일을 맡게 한다.

## 3. 저장소에는 어떤 종류가 있는가

저장소라고 해도 실제로는 성격이 다르다.

### 1. 블록 스토리지
운영체제나 데이터베이스가 디스크처럼 직접 다루는 저장 방식이다.

### 2. 파일 시스템 스토리지
폴더와 파일 경로 중심으로 저장하는 방식이다. 로컬 디렉토리나 NAS를 떠올리면 이해하기 쉽다.

### 3. 객체 스토리지
파일을 “경로상의 파일”보다 “키를 가진 객체”로 저장하는 방식이다. 메타데이터와 함께 저장하고, 보통 HTTP API로 접근한다.

### 왜 객체 스토리지가 중요해졌는가

웹 서비스가 커질수록 단순 로컬 파일 시스템만으로는 확장성과 운영 편의성이 부족해졌다. 여러 애플리케이션 인스턴스가 같은 파일에 접근해야 하거나, 버킷 단위 관리, 외부 공개 링크, 대용량 파일 저장 같은 요구가 늘어났기 때문이다.

이 문제를 해결하기 위해 S3 같은 **객체 스토리지** 가 널리 사용되기 시작했다.

## 4. 객체 스토리지는 왜 등장했는가

### 기존 문제

로컬 파일 시스템은 이해하기 쉽지만, 애플리케이션이 분산되거나 컨테이너로 나뉘면 파일 경로 관리가 어려워진다. 서버를 옮기거나 여러 인스턴스를 동시에 띄우면 “이 파일이 어느 컨테이너 안에 있지?” 같은 문제가 생긴다.

### 등장한 개념

이 문제를 해결하기 위해 **객체 스토리지(Object Storage)** 가 중요해졌다. 객체 스토리지는 파일을 디렉토리 트리 중심이 아니라, 고유한 key를 가진 object로 저장한다.

핵심 특징은 대체로 이렇다.

- HTTP API로 접근한다
- bucket 안에 object를 저장한다
- object key로 파일을 식별한다
- 메타데이터를 함께 다룰 수 있다
- 애플리케이션과 저장소가 느슨하게 연결된다

### Websidian에 대입

Websidian의 `files.object_key` 가 바로 이 객체 스토리지의 key 개념에 대응한다. DB는 이 key를 기억하고, 실제 파일 원본은 MinIO에서 조회한다. 

## 5. MinIO는 무엇인가

### 등장 배경

객체 스토리지가 필요해졌지만, 개인 홈랩이나 자체 호스팅 환경에서 매번 실제 AWS S3를 바로 쓰는 것이 항상 적절한 것은 아니다. 로컬 개발, 비용, 네트워크, 자율 운영, 실험 환경 측면에서 직접 운영 가능한 대안이 필요할 수 있다.

### 등장한 도구

**MinIO** 는 S3 호환 API를 제공하는 객체 스토리지 서버다. 즉, S3 스타일로 파일을 저장하고 읽는 방식을 로컬 또는 자체 서버 환경에서 운영할 수 있게 해준다. 

### Websidian에 대입

Websidian은 홈랩 + Docker Compose 기반 운영을 전제로 하므로, MinIO는 아주 잘 맞는 선택이다. 환경 변수 문서도 `MINIO_ENDPOINT`, `MINIO_ACCESS_KEY`, `MINIO_SECRET_KEY`, `MINIO_BUCKET`, `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD` 같은 값을 기준으로 구조를 잡고 있다. 

즉, MinIO는 “AWS를 흉내 내는 장난감”이 아니라, Websidian의 파일 저장 계층을 실제로 담당하는 핵심 인프라 중 하나다. 

## 6. bucket, object, object key는 무엇인가

### bucket
객체를 담는 큰 논리적 컨테이너다. 파일 시스템의 최상위 폴더처럼 느껴질 수 있지만, 더 정확히는 저장 공간의 묶음에 가깝다.

### object
실제로 저장되는 파일 단위다. 이미지, Markdown 파일, HTML 파일, PDF 모두 object가 될 수 있다.

### object key
bucket 안에서 object를 식별하는 문자열이다. 파일 경로처럼 보이게 만들 수도 있지만, 본질은 경로가 아니라 식별 key다.

예를 들어 이런 형태를 생각할 수 있다.

- `vaults/{vaultId}/documents/{documentId}/source/main.md`
- `vaults/{vaultId}/files/{fileId}/original/logo.png`
- `vaults/{vaultId}/documents/{documentId}/versions/3.html`

### Websidian에 대입

Websidian의 `files.object_key` 는 이 값을 저장하기 위한 컬럼이다. 이 값만 있으면 애플리케이션은 MinIO에서 실제 원본을 찾을 수 있다. 

## 7. 왜 파일 경로 대신 object key를 의식해야 하는가

### 기존 문제

로컬 파일 시스템에 익숙하면 경로(path) 중심으로 생각하기 쉽다. 하지만 객체 스토리지는 디렉토리 트리보다 key 기반 접근이 본질이다.

### 등장한 관점

그래서 애플리케이션은 “어느 로컬 경로에 파일이 있는가”보다 “어떤 bucket의 어떤 object key를 가리키는가”를 더 중요하게 다뤄야 한다.

### Websidian에 대입

이 관점이 있으면 나중에 저장소 구현이 바뀌어도 상위 계층은 덜 흔들린다. 즉, domain과 application 입장에서는 `objectKey` 를 다루고, 실제 MinIO SDK 호출은 infrastructure layer가 맡는 쪽이 더 깔끔하다. 

이것은 레이어드 아키텍처와도 잘 연결된다.

## 8. 메타데이터와 원본 파일은 각각 무엇을 맡는가

### 메타데이터(DB)

DB에는 보통 다음 같은 값이 들어간다.

- 파일 id
- vault id
- object key
- 원본 파일명
- MIME type
- 크기
- checksum
- 업로더
- 생성 시각 

### 원본 파일(MinIO)

MinIO에는 실제 바이너리나 텍스트 원본이 들어간다.

- Markdown 원문
- HTML 원문
- 이미지 파일
- PDF 파일
- 기타 첨부 파일 

### 왜 나누는가

이 분리가 있어야 다음이 쉬워진다.

- 빠른 메타데이터 조회
- 파일 원본의 독립적 관리
- 백업 전략 분리
- 파일 정리 정책 수립
- 향후 외부 스토리지 연동 확장 

## 9. Websidian에서 HTML은 파일인가 문서인가

### 기존 문제

일반적인 시스템에서는 HTML 파일도 그냥 파일 첨부처럼 취급하기 쉽다. 하지만 Websidian에서는 HTML이 단순 첨부가 아니라, Markdown과 같은 수준의 탐색 대상이 될 수 있다.

### 등장한 규칙

그래서 Websidian은 **HTML도 문서로 취급한다** 는 원칙을 갖는다. 즉, HTML은 단지 파일 자산이 아니라 `documents` 안에 들어갈 수 있는 document type이다. 

### 저장 관점에서 보면

이 말은 “HTML 원본은 저장소에 존재할 수 있지만, 시스템 의미상으로는 문서 노드”라는 뜻이다. 즉, 저장소 계층과 도메인 계층이 같은 질문에 같은 방식으로 답하지 않아도 된다.

- 저장소 관점: HTML 원본 파일은 object storage에 있을 수 있다
- 도메인 관점: HTML은 Document일 수 있다 

이 구분을 이해하면 Websidian의 설계가 훨씬 자연스럽게 보인다.

## 10. 왜 checksum, mime type, size 같은 메타데이터가 필요한가

### 기존 문제

파일은 단순히 “이름이 있는 바이트 덩어리”처럼 보일 수 있다. 하지만 운영 단계에서는 중복 업로드, 파일 손상, 잘못된 타입 처리, 렌더링 오류 같은 문제가 생긴다.

### 등장한 개념

그래서 파일 메타데이터를 함께 저장한다.

- `mime_type`: 어떤 종류의 파일인지 판별
- `size_bytes`: 파일 크기 확인
- `checksum`: 무결성 확인 또는 중복 판단 보조
- `original_name`: 사용자 친화적 이름 보존 

### Websidian에 대입

이 값들이 있어야 프론트엔드나 백엔드가 “이건 이미지인가?”, “이건 HTML 자산인가?”, “정상 업로드 되었는가?” 같은 질문에 답할 수 있다. 

## 11. 왜 업로드와 조회 흐름을 따로 이해해야 하는가

저장소는 단순히 파일을 넣는 장소가 아니라, 시스템 흐름 속에서 읽어야 한다.

### 문서/파일 업로드 흐름

1. 사용자가 문서 또는 첨부 파일을 업로드한다. 
2. Backend가 파일 메타데이터를 준비한다. 
3. 실제 원본은 MinIO에 저장한다. 
4. object key와 메타데이터를 DB에 기록한다. 
5. 필요하면 링크/임베드/버전 정보도 함께 저장한다. 

### 문서/파일 조회 흐름

1. Frontend가 문서 조회를 요청한다. 
2. Backend는 PostgreSQL에서 문서와 파일 메타데이터를 읽는다. 
3. 필요하면 object key를 바탕으로 MinIO 접근 정보를 만든다. 
4. Frontend는 Markdown/HTML/첨부 자산을 적절히 렌더링한다. 

업로드와 조회를 분리해서 보면, DB와 MinIO가 왜 동시에 필요한지 이해가 쉬워진다.

## 12. 왜 환경 변수가 중요한가

### 기존 문제

스토리지 연동 정보를 코드에 직접 넣으면 환경이 바뀔 때마다 수정이 필요하고, 액세스 키 같은 비밀값이 코드에 남을 위험이 생긴다.

### 등장한 개념

그래서 저장소 연결 정보는 환경 변수로 분리한다.

### Websidian에 대입

Websidian은 MinIO 관련 값을 환경 변수로 관리하는 방향이다. 예를 들면 아래 값들이 있다. 

- `MINIO_ENDPOINT`
- `MINIO_ACCESS_KEY`
- `MINIO_SECRET_KEY`
- `MINIO_BUCKET`
- `MINIO_ROOT_USER`
- `MINIO_ROOT_PASSWORD`
- `MINIO_API_PORT`
- `MINIO_CONSOLE_PORT` 

이 구조는 홈랩 환경에서도 중요하다. 개발/운영 환경의 주소, 포트, 계정이 달라져도 코드가 아니라 설정만 바꾸면 되기 때문이다. 

## 13. 왜 storage는 infrastructure 관심사인가

### 기존 문제

파일 저장 로직을 도메인 객체 안에 직접 넣기 시작하면, 시스템의 핵심 규칙이 저장 기술에 묶이게 된다.

### 등장한 관점

그래서 레이어드 아키텍처에서는 MinIO 연동 같은 구체 기술은 보통 **infrastructure layer** 에 둔다. 도메인과 애플리케이션은 “파일을 저장한다”, “object key를 참조한다” 같은 의미를 다루고, 실제 SDK 호출은 하위 계층이 맡는다.

### Websidian에 대입

Websidian의 domain model은 `File Asset` 과 `objectKey` 를 다루고, 실제 MinIO 연결 정보와 SDK 사용은 backend infrastructure 영역에 두는 쪽이 자연스럽다. 

이렇게 해야 나중에 저장소 구현이 바뀌거나 테스트 대체 구현을 넣기도 쉬워진다.

## 14. 개인 프로젝트에서 MinIO를 도입하는 이유

### 흔한 오해

혼자 개발하는 프로젝트에서는 로컬 디렉토리만 써도 충분해 보일 수 있다. 실제로 MVP 아주 초반에는 그럴 수도 있다.

### 그래도 MinIO가 좋은 이유

Websidian은 처음부터 문서 원본, 첨부파일, HTML 자산, 이미지 등을 장기적으로 다뤄야 하고, 홈랩 + Docker Compose 환경에서 운영될 것을 전제로 한다. 이런 전제에서는 객체 스토리지 개념을 일찍 잡아두는 것이 오히려 나중 비용을 줄인다. 

### Websidian 관점의 장점

- 운영 구조가 실제 목표 환경과 가깝다
- DB와 파일 저장 책임이 분리된다
- 나중에 버킷 정책, 공개/비공개 처리, 정리 정책으로 확장하기 쉽다
- 문서와 파일의 경계를 코드에서 더 명확히 유지할 수 있다 

즉, 이 프로젝트에서 MinIO는 과한 복잡도가 아니라, 장기 목표를 미리 무리 없이 받아들이는 정도의 현실적 선택이다.

## 15. 지금 단계에서 꼭 잡아야 할 핵심 문장

아래 문장만 정확히 이해해도 저장소 감각은 많이 잡힌다.

- 모든 데이터를 데이터베이스 하나에 넣는 것이 항상 좋은 구조는 아니다. 
- 구조적 메타데이터와 파일 원본은 서로 다른 성격의 저장 문제다. 
- 객체 스토리지는 파일을 path보다 key 중심으로 다루는 저장 방식이다. 
- MinIO는 S3 호환 객체 스토리지를 홈랩과 로컬 환경에서 운영하기 좋게 해준다. 
- Websidian은 PostgreSQL에 메타데이터를, MinIO에 실제 파일 원본을 두는 구조를 전제로 한다. 
- HTML은 저장소 관점에서는 파일일 수 있지만, 도메인 관점에서는 문서가 될 수 있다.
