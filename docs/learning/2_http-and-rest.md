# HTTP and REST

## Purpose

이 문서는 Websidian을 구현하기 전에 알아두면 좋은 HTTP와 REST의 기본 개념을 정리한다.

설명 방식은 가능한 한 다음 흐름을 따른다.

- 기존에는 무엇이 문제였는가
- 그 문제를 해결하기 위해 어떤 개념이 등장했는가
- 그 개념은 실제로 무엇을 해결하는가
- Websidian에서는 이 개념이 어디에 연결되는가

이 문서는 학습 문서다. 실제 Websidian API의 공식 방향은 `docs/backend/api-overview.md`를 따른다.

## 1. 왜 HTTP를 먼저 알아야 하는가

웹에서 브라우저와 서버는 서로 떨어진 곳에서 동작한다. 따라서 둘이 대화하려면 공통된 언어와 절차가 필요하다.

초기의 문제는 단순하다. 브라우저는 어떤 문서를 받고 싶고, 서버는 어떤 내용을 돌려줘야 하는데, 요청과 응답의 형식이 통일되어 있지 않으면 서로 통신할 수 없다.

이 문제를 해결하기 위해 웹에서는 **HTTP**가 표준적인 통신 규약으로 자리 잡았다. HTTP는 브라우저와 서버가 “무엇을 요청하고, 어떤 결과를 받는가”를 정하는 약속이다. 

즉, REST를 이해하기 전에 먼저 알아야 하는 것은 “REST는 HTTP 위에서 동작하는 설계 스타일”이라는 점이다. REST가 건물의 설계 원칙이라면, HTTP는 그 건물이 서 있는 지반에 가깝다.

## 2. HTTP란 무엇인가

### 기존 문제

네트워크 상에서 서로 다른 프로그램이 통신하려면 최소한 아래가 정해져 있어야 한다.

- 어디에 요청할 것인가
- 무엇을 하려는가
- 어떤 데이터를 보낼 것인가
- 성공인지 실패인지 어떻게 알 것인가

이런 기준이 없으면 브라우저 제작사, 서버 제작사, 언어, 운영체제가 모두 달라질 때 웹은 통일성을 잃는다.

### 등장한 개념

이 문제를 해결하기 위해 HTTP는 다음 요소를 표준화했다.

- **URL**: 어디에 요청할 것인가
- **Method**: 무엇을 하려는가
- **Header**: 요청/응답에 붙는 부가 정보
- **Body**: 실제 데이터
- **Status Code**: 결과가 어땠는가

### 핵심 정의

HTTP는 **요청(Request)과 응답(Response)** 으로 이루어진다.

- 클라이언트(브라우저, 프론트엔드 앱, 모바일 앱 등)가 요청을 보낸다.
- 서버가 그 요청을 처리한다.
- 서버가 응답을 돌려준다.

이 단순한 왕복 구조가 웹의 거의 모든 동작의 바탕이다. 

## 3. 요청과 응답

### 요청(Request)

HTTP 요청은 보통 아래 요소를 가진다.

- **메서드(Method)**: 조회인지, 생성인지, 수정인지, 삭제인지
- **URL**: 요청 대상 주소
- **헤더(Header)**: 콘텐츠 형식, 인증 정보 등
- **바디(Body)**: 서버에 보낼 실제 데이터

예를 들어 문서를 조회할 때는 다음처럼 생각할 수 있다.

- 메서드: `GET`
- URL: `/api/v1/documents/123`
- 헤더: `Accept: application/json`
- 바디: 없음

### 응답(Response)

HTTP 응답은 보통 아래 요소를 가진다.

- **상태 코드(Status Code)**: 결과를 숫자로 표현
- **헤더(Header)**: 응답 타입 등 부가 정보
- **바디(Body)**: 실제 응답 데이터(JSON, HTML, 파일 등)

문서 조회 성공 응답은 이런 느낌이다.

- 상태 코드: `200 OK`
- 헤더: `Content-Type: application/json`
- 바디: 문서 정보 JSON

Websidian API도 이런 요청/응답 구조를 전제로 설계된다. 

## 4. 왜 메서드가 필요한가

### 기존 문제

만약 모든 요청이 단순히 “주소만 호출”하는 방식이라면, 서버는 같은 URL에 대해 조회를 원하는지, 생성을 원하는지, 수정을 원하는지 구분하기 어렵다.

예를 들어 `/documents`라는 주소 하나만 있을 때 다음 의도를 구분할 방법이 필요하다.

- 문서 목록을 보고 싶다
- 새 문서를 만들고 싶다
- 문서를 삭제하고 싶다

### 등장한 개념

이 문제를 해결하기 위해 HTTP는 **메서드(Method)** 를 도입했다.

대표적으로:

- `GET`: 조회
- `POST`: 생성
- `PUT`: 전체 교체 성격의 수정
- `PATCH`: 일부 수정
- `DELETE`: 삭제 

### 왜 좋은가

메서드를 사용하면 같은 자원이라도 “무슨 행동을 하려는지”를 명확하게 분리할 수 있다.

예:

- `GET /api/v1/vaults` → Vault 목록 조회
- `POST /api/v1/vaults` → Vault 생성 

즉, URL은 **대상**, 메서드는 **행동 종류**를 나타낸다.

## 5. 왜 상태 코드가 필요한가

### 기존 문제

서버가 응답을 보냈다고 해서 항상 성공한 것은 아니다. 요청 형식이 잘못되었을 수도 있고, 대상 문서가 없을 수도 있고, 로그인하지 않아 거부되었을 수도 있다.

그런데 응답 결과를 매번 텍스트 문장으로만 표현하면, 클라이언트는 자동으로 처리하기 어렵다.

### 등장한 개념

이 문제를 해결하기 위해 HTTP는 **상태 코드(Status Code)** 를 사용한다. 숫자 코드로 성공/실패의 종류를 빠르게 구분할 수 있다.

Websidian 문서에서 정리한 대표 코드는 다음과 같다. 

- `200 OK`: 일반 조회/수정 성공
- `201 Created`: 생성 성공
- `204 No Content`: 성공했지만 응답 본문 없음
- `400 Bad Request`: 요청이 잘못됨
- `401 Unauthorized`: 인증 필요
- `403 Forbidden`: 권한 없음
- `404 Not Found`: 대상 없음
- `409 Conflict`: 상태 충돌
- `422 Unprocessable Entity`: 의미적으로 잘못된 입력
- `500 Internal Server Error`: 서버 내부 오류 

### 왜 좋은가

프론트엔드는 상태 코드만 보고도 기본적인 분기를 할 수 있다.

- `200`이면 데이터 렌더링
- `404`면 “문서를 찾을 수 없음” 화면 표시
- `401`이면 로그인 유도
- `500`이면 일반 오류 메시지 표시

즉, 상태 코드는 사람이 읽는 설명 이전에 프로그램이 판단하기 위한 빠른 신호다.

## 6. 왜 JSON이 중요해졌는가

### 기존 문제

초기의 웹은 서버가 HTML을 완성해서 내려주는 방식이 많았다. 이 방식은 브라우저가 곧바로 화면을 보여주기에는 좋지만, 프론트엔드가 데이터를 세밀하게 조립하거나 여러 클라이언트에서 같은 데이터를 재사용하기에는 불편했다.

### 등장한 개념

그래서 데이터 교환 포맷으로 **JSON**이 널리 쓰이게 되었다. JSON은 사람이 읽기 쉽고, JavaScript와 잘 맞고, 다양한 언어에서 다루기 쉬운 구조다.

예:

```json
{
  "id": "doc-123",
  "title": "My Note",
  "type": "markdown"
}
```

### Websidian에 대입

Websidian API도 요청/응답 기본 포맷으로 JSON을 사용한다. 

그 이유는 다음과 같다.

- Vue 프론트엔드가 다루기 쉽다. 
- Spring Boot에서 직렬화/역직렬화가 쉽다. 
- 문서 메타데이터, 링크, 첨부 요약 같은 구조화된 데이터를 표현하기 좋다. 

## 7. API란 무엇인가

### 기존 문제

프론트엔드와 백엔드가 분리되면, 서로 데이터를 주고받는 규칙이 필요하다. 단순히 “서버 함수를 직접 호출”하는 방식은 네트워크 환경에서는 통하지 않는다.

### 등장한 개념

이 문제를 해결하는 것이 **API(Application Programming Interface)** 다. 프로그램이 다른 프로그램과 소통하는 공식적인 통로라고 보면 된다.

웹에서 API는 보통 다음과 같은 역할을 한다.

- 프론트엔드가 백엔드에 데이터 요청
- 백엔드가 결과를 JSON으로 응답
- 프론트엔드가 그 데이터를 이용해 화면 렌더링

### Websidian에 대입

Websidian은 문서 플랫폼이므로, API의 중심은 “문서와 파일을 어떻게 주고받을 것인가”에 있다. Vault, Document, File, Link, Tag 같은 리소스를 일관되게 노출해야 한다. 

즉, API는 Websidian에서 프론트엔드와 백엔드의 경계면이다. 

## 8. REST는 왜 등장했는가

### 기존 문제

API가 필요하다는 것까지는 이해했더라도, 여전히 문제가 남는다. API를 어떤 규칙으로 설계할지 정하지 않으면 팀이나 프로젝트마다 스타일이 제각각이 된다.

예를 들어 아래처럼 뒤섞일 수 있다.

- `/getVaultList`
- `/createVault`
- `/document/read/123`
- `/file-download?id=10`

이런 방식은 처음엔 만들기 쉬워 보여도, 규모가 커질수록 규칙성이 약해진다. 어떤 URL이 목록인지, 어떤 URL이 생성인지, 어느 정도 패턴이 일관된지 파악하기 어려워진다.

### 등장한 개념

이 문제를 해결하려는 대표적인 스타일 중 하나가 **REST**다.

REST는 “웹의 기본 요소(HTTP, URL, 자원 식별)를 최대한 자연스럽게 활용해서 API를 설계하자”는 방향의 스타일이다. Websidian도 초기 단계에서 이 REST 스타일을 사용한다. 

### 핵심 아이디어

REST는 보통 다음 원칙으로 이해하면 충분하다.

- **리소스 중심 URL** 사용 
- **HTTP 메서드의 의미를 그대로 사용** 
- **JSON 같은 표준 포맷 사용** 
- **서버는 stateless하게 동작** 

즉, URL은 자원을 표현하고, 메서드는 행동을 표현한다.

## 9. 리소스 중심 URL이란 무엇인가

### 기존 문제

기존의 함수 호출식 URL은 “행동”이 URL 이름 안에 섞인다. 그러면 URL 규칙이 코드 작성자 취향에 따라 달라지고, 자원의 구조를 파악하기 어렵다.

### 등장한 개념

REST는 URL에서 **무엇을 조작하는가** 를 드러내도록 한다. 즉, 행동보다 **대상 리소스** 를 URL에 담는다.

예:

- `/api/v1/vaults`
- `/api/v1/vaults/{vaultId}`
- `/api/v1/documents/{documentId}`
- `/api/v1/files/{fileId}` 

### 왜 좋은가

이런 URL은 구조가 보인다.

- `vaults`는 Vault 집합
- `vaults/{id}`는 특정 Vault 하나
- `documents/{id}/versions`는 특정 문서의 버전 목록 

즉, API를 읽는 사람 입장에서 “시스템이 어떤 자원으로 이루어져 있는지”를 URL만 봐도 유추할 수 있다.

### Websidian에 대입

Websidian의 핵심 리소스는 Vault, Document, File, Link, Tag, User, Permission 등으로 정리되어 있다. 이 중 MVP에서는 Vault, Document, File이 가장 중요하다. 

따라서 REST 스타일은 Websidian의 도메인 구조를 URL에 비교적 자연스럽게 반영할 수 있다.

## 10. Stateless는 왜 중요할까

### 기존 문제

서버가 매 요청 사이의 상태를 너무 많이 기억해야 하면, 시스템이 복잡해지고 확장성이 떨어진다. 어떤 요청이 성공하려면 “그 전에 서버가 어떤 상태를 기억하고 있어야 하는지”를 계속 추적해야 하기 때문이다.

### 등장한 개념

REST 스타일은 보통 서버가 **stateless** 하게 동작하는 것을 강조한다. 이는 “각 요청이 필요한 정보를 충분히 담고 있고, 서버는 이전 요청의 대화 맥락에 덜 의존한다”는 뜻이다. 

### 왜 좋은가

- 서버 확장이 단순해진다.
- 문제 추적이 쉬워진다.
- 요청 하나만 봐도 어느 정도 상황을 파악할 수 있다.

물론 현실에서는 인증/세션 같은 요소 때문에 완전히 상태가 없다고 말하기는 어렵지만, 설계 원칙으로서 stateless 지향은 API를 단순하게 유지하는 데 도움을 준다. 

## 11. 왜 버저닝이 필요한가

### 기존 문제

API는 시간이 지나면서 바뀐다. 응답 필드가 바뀌고, URL 구조가 달라지고, 더 이상 호환되지 않는 변경이 생길 수 있다.

그런데 버전 구분 없이 API를 바꾸면, 기존 프론트엔드가 갑자기 깨질 수 있다.

### 등장한 개념

그래서 API에는 **버저닝(versioning)** 이 필요하다. Websidian은 URL prefix 기반 버저닝을 사용한다. 

형식:

- `/api/v1/...` 

### 왜 좋은가

Websidian 문서에 정리된 이유는 다음과 같다. 

- 프론트엔드와 백엔드 계약을 명확히 할 수 있다.
- 나중에 breaking change가 생겨도 새 버전을 병행할 수 있다.
- 내부 프로젝트에서도 규칙을 단순하게 유지할 수 있다.

즉, 버저닝은 “미래의 변경을 지금부터 관리하기 위한 안전장치”다.

## 12. 왜 에러 응답 구조를 통일해야 하는가

### 기존 문제

상태 코드만으로는 부족한 경우가 있다. 예를 들어 둘 다 `404`여도, 문서가 없는 것인지, Vault가 없는 것인지, 링크 대상이 없는 것인지 클라이언트가 더 자세히 알아야 할 수 있다.

### 등장한 개념

그래서 많은 API는 **구조화된 에러 응답 본문**을 함께 사용한다. Websidian도 stack trace를 그대로 노출하지 않고, 클라이언트가 처리 가능한 형태의 에러 구조를 유지하는 방향을 택한다. 

예시:

```json
{
  "error": {
    "code": "DOCUMENT_NOT_FOUND",
    "message": "The requested document does not exist.",
    "details": null
  }
}
```

### 왜 좋은가

- 프론트엔드가 에러 종류별로 분기하기 쉽다.
- 사용자 친화적인 메시지로 변환하기 쉽다.
- 디버깅과 로그 분석이 쉬워진다.

즉, 상태 코드는 “큰 분류”, 에러 JSON은 “세부 설명” 역할을 한다.

## 13. 왜 페이지네이션이 필요한가

### 기존 문제

리스트 데이터가 많아지면 한 번에 전부 내려주는 방식은 비효율적이다. 응답이 무거워지고, 화면도 느려지고, 네트워크 비용도 커진다.

### 등장한 개념

이 문제를 해결하기 위해 목록성 API는 **페이지네이션(pagination)** 을 사용한다. Websidian의 초기 규칙은 `page`, `size`, `sort` 같은 표준 파라미터를 사용하는 것이다. 

예:

- `GET /api/v1/vaults?page=1&size=20`
- `GET /api/v1/documents?status=published&sort=updatedAt,desc` 

### 왜 좋은가

- 한 번에 필요한 만큼만 가져올 수 있다.
- 목록 화면 성능이 안정적이다.
- 정렬과 필터링을 조합하기 쉽다.

지금 당장은 작은 데이터셋이라 체감이 적을 수 있지만, 문서 수가 많아질수록 중요한 개념이다. 

## 14. Websidian에서 REST가 어떻게 쓰일까

Websidian API 문서 기준으로, 초기 핵심 리소스는 다음과 같다. 

- Vault
- Document
- Document Version
- File
- Link
- Tag
- User
- Permission 

MVP 관점에서는 Vault, Document, File이 가장 중요하고, Link는 문서 파싱 결과를 반영하는 보조 리소스로 본다. 

대표 예시는 아래와 같다. 

- `GET /api/v1/vaults` → Vault 목록 조회
- `POST /api/v1/vaults` → Vault 생성
- `GET /api/v1/vaults/{vaultId}` → Vault 상세 조회
- `GET /api/v1/documents/{documentId}` → 문서 조회
- `POST /api/v1/vaults/{vaultId}/documents` → 특정 Vault 아래 문서 생성
- `GET /api/v1/files/{fileId}/download` → 파일 다운로드 URL 발급 

이 구조를 보면 Websidian의 도메인 모델이 그대로 API 표면으로 드러난다는 것을 알 수 있다.

## 15. REST가 만능은 아닌가

REST는 매우 널리 쓰이고 이해하기 쉬운 스타일이지만, 모든 문제의 유일한 해답은 아니다. GraphQL, gRPC, RPC 스타일 API 같은 다른 접근도 있다.

하지만 Websidian의 현재 단계에서는 REST가 적합하다. 이유는 다음과 같다. 

- 개인 프로젝트에서 이해하고 유지하기 쉽다.
- 리소스 중심 구조가 Vault/Document/File 같은 도메인에 잘 맞는다.
- Vue 프론트엔드와 Spring Boot 백엔드 사이 계약을 단순하게 유지할 수 있다. 
- 문서화와 구현을 동시에 진행하기 좋다. 

즉, 지금 Websidian에서 REST를 선택한 것은 “세상에서 가장 고급 기술”이라서가 아니라, **현재 문제를 가장 단순하고 명확하게 해결해 주기 때문**이다.

## 16. 지금 단계에서 꼭 잡아야 할 핵심 문장

아래 문장들만 정확히 이해해도 HTTP와 REST의 큰 틀은 잡힌다.

- HTTP는 브라우저와 서버가 요청/응답을 주고받는 규칙이다.
- 메서드는 행동 종류를, URL은 대상을 표현한다.
- 상태 코드는 결과를 프로그램이 이해하기 쉽게 전달한다. 
- JSON은 프론트엔드와 백엔드가 구조화된 데이터를 교환하기 좋은 형식이다. 
- API는 프로그램 사이의 공식 통로다. 
- REST는 HTTP의 기본 요소를 최대한 자연스럽게 활용해 API를 설계하는 스타일이다. 
- Websidian은 REST 스타일, `/api/v1` 버전 prefix, JSON 응답을 기본으로 사용한다.
