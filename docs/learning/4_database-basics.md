# Database Basics

## Purpose

이 문서는 Websidian을 구현하기 전에 알아두면 좋은 데이터베이스의 기본 개념을 정리한다.

설명 방식은 가능한 한 다음 흐름을 따른다.

- 기존에는 무엇이 문제였는가
- 그 문제를 해결하기 위해 어떤 개념이 등장했는가
- 그 개념은 실제로 무엇을 해결하는가
- Websidian에서는 이 개념이 어디에 연결되는가

이 문서는 학습 문서다. 실제 Websidian의 데이터 구조 방향은 `docs/database/erd-overview.md`, `docs/database/schema-draft.md`, `docs/architecture/domain-model.md` 문서를 기준으로 본다. 

## 1. 왜 데이터베이스가 필요한가

### 기존 문제

프로그램이 아주 단순할 때는 메모리 변수, 텍스트 파일, JSON 파일만으로도 데이터를 다룰 수 있다. 하지만 사용자가 늘고 데이터가 쌓이기 시작하면 곧 문제가 생긴다.

- 프로그램을 재시작하면 메모리 데이터가 사라진다
- 파일 여러 개에 데이터가 흩어진다
- 같은 데이터를 여러 곳에서 수정하다가 불일치가 생긴다
- 검색, 정렬, 필터링이 점점 느려진다
- 여러 사용자가 동시에 수정할 때 충돌이 생긴다

즉, “데이터를 저장한다”와 “데이터를 안정적으로 관리한다”는 전혀 다른 문제다.

### 등장한 개념

이 문제를 해결하기 위해 **데이터베이스(Database)** 라는 개념이 중요해졌다. 데이터베이스는 단순 저장소가 아니라, 데이터를 **지속적으로 저장하고, 구조화하고, 조회하고, 무결성을 유지하는 시스템**이다.

### Websidian에 대입

Websidian에서는 PostgreSQL이 이 역할을 맡는다. 다만 중요한 점은 PostgreSQL이 모든 것을 저장하는 곳은 아니라는 것이다. Websidian은 문서와 파일의 메타데이터, 관계, 권한, 버전 정보는 DB에 두고, 실제 바이너리 파일 원본은 MinIO에 두는 방향을 잡고 있다. 

## 2. 왜 “그냥 파일로 저장”하면 안 되는가

### 기존 문제

처음에는 파일 하나에 JSON으로 저장하는 방식이 단순하고 직관적으로 보인다. 하지만 시스템이 커지면 “파일이 곧 데이터 구조”가 되어버린다.

예를 들어 문서 시스템에서 아래 질문에 답하려면 금방 복잡해진다.

- 이 Vault의 문서는 몇 개인가
- 이 문서의 최신 버전은 무엇인가
- 어떤 문서가 이 문서를 링크하고 있는가
- 이 태그가 붙은 문서만 모아 보여줄 수 있는가

파일 기반 저장은 원본 보관에는 좋을 수 있지만, **관계 조회**와 **일관성 유지**에는 약하다.

### 등장한 개념

그래서 데이터를 단순 파일 덩어리가 아니라 **구조화된 스키마와 관계**로 다루는 방식이 필요해졌다. 관계형 데이터베이스는 바로 이 문제를 해결하려고 발전해 왔다.

### Websidian에 대입

Websidian의 핵심은 “파일 저장”보다 “문서 관계와 탐색 경험”에 있다. 그래서 Vault, Document, Version, Link, Tag, Permission 같은 개념을 구조화해 저장하는 것이 중요하다. 

## 3. 데이터 모델은 왜 먼저 생각해야 하는가

### 기존 문제

기능부터 급하게 만들면, 나중에 데이터 구조가 기능을 발목 잡는 경우가 많다. 예를 들어 초기에 문서와 파일의 차이를 흐리게 저장해 두면, 나중에 그래프 뷰나 링크 추적, HTML 문서 지원에서 계속 예외가 생긴다.

### 등장한 개념

그래서 구현 전에 먼저 **도메인 모델** 과 **ERD(Entity Relationship Diagram)** 를 생각하는 습관이 중요해졌다. 먼저 “우리가 무엇을 다루는 시스템인가”를 정리하고, 그 뒤에 “그 개념을 테이블로 어떻게 옮길까”를 생각하는 흐름이다.

### Websidian에 대입

Websidian 문서도 같은 순서를 따른다. 먼저 `domain-model.md` 에서 Vault, Document, File Asset, Link Relation, Version 같은 도메인 개념을 정의하고, 그 다음 `erd-overview.md`, `schema-draft.md` 에서 이를 테이블 구조로 내린다. 

즉, DB 설계는 SQL 문법을 먼저 쓰는 일이 아니라, **도메인 개념을 데이터 구조로 번역하는 일**에 가깝다.

## 4. 관계형 데이터베이스는 왜 등장했는가

### 기존 문제

초기 데이터 관리 방식은 파일 중심이거나, 프로그램 내부 구조에 지나치게 묶여 있는 경우가 많았다. 이 방식은 데이터의 중복, 검색의 어려움, 구조 변경의 불편함을 자주 만들었다.

### 등장한 개념

이 문제를 해결하기 위해 **관계형 데이터베이스(Relational Database)** 가 널리 쓰이게 되었다. 핵심 생각은 데이터를 표(table) 형태로 나누고, 표들 사이의 관계를 명시적으로 관리하자는 것이다.

### 왜 좋은가

- 데이터를 정리된 형태로 다룰 수 있다
- 중복을 줄일 수 있다
- 관계를 명시할 수 있다
- 조건 검색과 조인이 가능하다
- 제약조건으로 데이터 무결성을 보호할 수 있다

### Websidian에 대입

Websidian의 데이터는 관계형 구조와 잘 맞는다.

- 한 Vault는 여러 Document를 가진다
- 한 Document는 여러 Version을 가진다
- 한 Document는 여러 Tag를 가질 수 있다
- Document와 Document 사이에는 Link가 있다
- Document와 File 사이에는 참조 관계가 있다 

이런 구조는 전형적인 관계형 모델 문제다.

## 5. 테이블, 행, 열은 무엇인가

### 등장 배경

데이터를 구조적으로 저장하려면 가장 기본 단위가 필요하다. 관계형 DB에서는 이 기본 단위를 보통 아래처럼 본다.

- **테이블(table)**: 같은 종류의 데이터를 모아두는 틀
- **행(row)**: 실제 데이터 한 건
- **열(column)**: 데이터의 속성 하나

### 예시

예를 들어 `documents` 테이블이 있다면:

- 테이블: documents
- 행: 특정 문서 한 개
- 열: id, vault_id, slug, title, document_type, status 등 

### 중요한 관점

테이블은 단순한 엑셀 시트처럼 보일 수 있지만, 실제로는 도메인 개념의 저장 단위다. 그래서 좋은 테이블 설계는 “컬럼을 많이 넣는 것”보다 “무슨 개념을 한 테이블로 볼 것인가”를 잘 나누는 것이 중요하다.

## 6. 왜 기본키(Primary Key)가 필요한가

### 기존 문제

데이터를 저장하면 곧 “각 행을 어떻게 구분할 것인가”라는 문제가 생긴다. 제목이나 이름만으로는 중복이 생길 수 있고, 나중에 값이 바뀔 수도 있다.

### 등장한 개념

그래서 **기본키(Primary Key)** 가 필요해졌다. 기본키는 각 행을 유일하게 식별하는 값이다.

### Websidian에 대입

Websidian의 스키마 초안도 핵심 테이블마다 단일 기본키 `id`를 두는 방향을 잡고 있다. 타입은 UUID 또는 bigint를 후보로 두고 있지만, 핵심은 사람이 읽는 이름과 별개로 시스템이 신뢰할 식별자를 둔다는 점이다. 

### 왜 중요한가

- 특정 행을 안정적으로 참조할 수 있다
- 다른 테이블이 외래키로 연결할 수 있다
- 이름이나 slug가 바뀌어도 내부 식별은 유지된다

## 7. 왜 외래키(Foreign Key)가 필요한가

### 기존 문제

한 테이블 안에 모든 데이터를 몰아넣지 않으면, 서로 다른 테이블 사이의 연결을 표현해야 한다. 그런데 이 연결을 단순 숫자나 문자열로만 두면 잘못된 참조가 생길 수 있다.

예를 들어 존재하지 않는 `vault_id` 를 가진 문서가 들어가면 시스템 의미가 깨진다.

### 등장한 개념

그래서 **외래키(Foreign Key)** 가 등장한다. 외래키는 “이 값은 다른 테이블의 특정 행을 가리켜야 한다”는 관계 규칙이다.

### Websidian에 대입

- `documents.vault_id` 는 특정 `vaults.id` 를 가리킨다
- `document_versions.document_id` 는 특정 `documents.id` 를 가리킨다
- `vaults.entry_document_id` 는 특정 문서를 가리키되, 같은 Vault 내부 문서여야 한다 

### 왜 중요한가

외래키는 단순 연결 이상의 의미가 있다. 이것은 “잘못된 데이터가 들어오지 않게 막는 안전장치”다.

## 8. 왜 정규화라는 개념이 등장했는가

### 기존 문제

처음에는 한 테이블에 많은 정보를 넣는 것이 편해 보인다. 하지만 중복 데이터가 늘어나면 수정 누락, 값 불일치, 삭제 시 정보 손실 같은 문제가 생긴다.

예를 들어 문서 행마다 Vault 이름을 같이 저장하면, Vault 이름이 바뀔 때 관련 문서를 모두 수정해야 한다. 하나라도 놓치면 데이터가 서로 달라진다.

### 등장한 개념

이 문제를 해결하기 위해 **정규화(Normalization)** 라는 개념이 발전했다. 정규화는 데이터를 적절히 분리해 중복을 줄이고, 관계로 연결해 일관성을 높이려는 설계 방식이다.

### 너무 오해하지 말 점

정규화는 “무조건 최대한 잘게 쪼개라”는 뜻이 아니다. 중요한 것은 **의미가 다른 데이터를 분리하고, 중복 때문에 생기는 문제를 줄이는 것**이다.

### Websidian에 대입

Websidian 문서도 완벽한 정규화보다 “핵심 도메인 개념을 안정적으로 담을 수 있는 구조”를 우선하자고 본다. 즉, 개인 프로젝트와 MVP 단계에서는 이론적 완벽함보다 현실적 균형이 중요하다. 

## 9. 왜 조인(Join)이 필요한가

### 기존 문제

데이터를 분리해 저장하면, 나중에 다시 합쳐서 읽어야 하는 순간이 온다. 예를 들어 문서 목록을 보여줄 때 문서 정보뿐 아니라 Vault 정보, 현재 버전 정보가 함께 필요할 수 있다.

### 등장한 개념

그래서 관계형 DB에서는 **조인(Join)** 이라는 개념이 중요하다. 조인은 서로 관련된 테이블을 조건에 따라 연결해서 하나의 결과처럼 읽는 방식이다.

### Websidian 예시

문서 상세 조회에서는 이런 연결이 생길 수 있다.

- `documents` 와 `vaults`
- `documents` 와 `document_versions`
- `documents` 와 `document_links`
- `documents` 와 `document_tags` / `tags` 

즉, 데이터를 잘 나누는 것과 잘 다시 묶어 읽는 것은 한 쌍의 문제다.

## 10. 왜 인덱스(Index)가 필요한가

### 기존 문제

데이터가 적을 때는 어떤 조건으로 검색해도 빨라 보인다. 하지만 행 수가 커지면 매번 처음부터 끝까지 훑는 방식은 금방 느려진다.

### 등장한 개념

이 문제를 해결하기 위해 **인덱스(Index)** 가 등장한다. 인덱스는 책의 맨 뒤 색인처럼, 원하는 값을 더 빨리 찾기 위한 보조 구조다.

### Websidian에 대입

스키마 초안에서도 아래 인덱스 후보를 먼저 잡고 있다. 

- `vaults(slug)`
- `documents(vault_id, slug)`
- `documents(vault_id, status)`
- `document_versions(document_id, version_no desc)`
- `document_links(source_document_id)`
- `document_links(target_document_id)`
- `tags(vault_id, normalized_name)` 

### 왜 중요한가

Websidian은 나중에 문서 탐색, 링크 추적, 태그 조회, 대표 문서 조회가 많아질 수 있다. 이런 시스템에서는 인덱스가 단순 성능 최적화가 아니라, **사용 경험을 지키는 기본 장치**가 된다.

## 11. 왜 무결성(Integrity)이 중요한가

### 기존 문제

데이터는 저장되기만 하면 끝이 아니다. 시간이 지나면 잘못된 참조, 중복된 slug, 존재하지 않는 최신 버전 참조 같은 문제가 누적될 수 있다.

### 등장한 개념

그래서 데이터베이스 설계에서는 **무결성(Integrity)** 이 중요하다. 무결성은 데이터가 논리적으로 일관되고, 시스템 규칙을 어기지 않는 상태를 말한다.

### Websidian에서 중요한 규칙

- 문서는 반드시 Vault에 속해야 한다
- 대표 문서는 같은 Vault 내부 문서여야 한다
- 현재 버전은 해당 문서의 버전이어야 한다
- 같은 Vault 안에서 document slug는 유일해야 한다
- `files.object_key` 는 유일해야 한다 

이런 규칙은 그냥 개발자 머릿속에만 두면 안 된다. 가능한 것은 DB 제약조건으로, 나머지는 애플리케이션 규칙으로 지켜야 한다.

## 12. 왜 ERD가 필요한가

### 기존 문제

테이블이 몇 개 안 될 때는 머릿속으로 관계를 기억할 수 있다. 하지만 엔티티가 많아지면 관계를 빠뜨리거나, 같은 개념을 중복 정의하거나, 연결 방향을 착각하기 쉽다.

### 등장한 개념

그래서 **ERD(Entity Relationship Diagram)** 가 중요해진다. ERD는 테이블과 관계를 시각적으로 정리해, 구현 전에 구조를 검토할 수 있게 해준다.

### Websidian에 대입

Websidian의 ERD 개요는 다음 원칙을 강조한다. 

- 문서와 파일을 구분한다
- 관계를 명시적으로 기록한다
- 버전은 별도 엔티티로 관리한다
- Vault를 최상위 경계로 둔다 

즉, ERD는 그림을 예쁘게 그리기 위한 것이 아니라, **빠진 관계와 잘못된 모델링을 일찍 발견하기 위한 도구**다.

## 13. Websidian에서 중요한 핵심 테이블은 무엇인가

초기 설계 기준으로 먼저 이해해야 할 핵심 테이블은 아래 정도다. 

- `vaults`: 문서 저장소의 최상위 단위
- `documents`: 읽고 탐색하는 기본 문서 엔티티
- `document_versions`: 문서 내용의 버전 스냅샷
- `files`: 첨부파일 메타데이터
- `document_links`: 문서 간 링크/임베드 관계
- 이후 확장: `tags`, `document_tags`, `permissions`, `document_file_refs` 

이 순서가 중요한 이유는, Websidian의 본질이 “문서와 그 관계”이기 때문이다. 그래서 테이블도 기능 화면보다 먼저, 핵심 개념 중심으로 이해하는 편이 좋다. 

## 14. 왜 문서와 파일을 구분해야 하는가

### 기존 문제

처음 보면 Markdown 파일도 파일이고 HTML 파일도 파일이며 이미지도 파일이니, 전부 한 종류로 저장하고 싶어질 수 있다. 하지만 그렇게 하면 탐색의 대상과 첨부 자산의 대상이 섞인다.

### 등장한 개념

그래서 Websidian은 **문서(Document)** 와 **파일(File Asset)** 을 구분한다. 문서는 읽고 이동하고 링크하고 그래프를 그리는 대상이고, 파일은 문서가 참조하는 자산이다. 단, HTML은 예외적으로 문서가 될 수 있다. 

### 왜 중요한가

이 구분이 있어야 나중에 다음이 가능해진다.

- 문서 그래프 뷰
- 백링크 계산
- entry document 지정
- HTML 문서를 Markdown과 같은 수준에서 탐색
- 파일 첨부와 문서 노드를 다르게 처리 

이것은 Websidian 데이터 모델의 핵심 특징 중 하나다.

## 15. 왜 버전을 별도 테이블로 두는가

### 기존 문제

문서 본문을 한 행에 덮어쓰는 방식만 쓰면, 과거 상태를 알 수 없고 롤백도 어렵다. “누가 언제 무엇을 바꿨는가”도 남기기 어렵다.

### 등장한 개념

그래서 **버전 엔티티** 를 별도로 둔다. 현재 문서와 변경 이력을 분리하면, 현재 상태와 과거 기록을 모두 안정적으로 관리할 수 있다.

### Websidian에 대입

Websidian은 `documents` 와 `document_versions` 를 분리하고, 현재 사용 중인 버전은 `documents.current_version_id` 로 가리키는 구조를 잡고 있다. 

### 왜 좋은가

- 현재 상태 조회가 명확하다
- 히스토리를 남길 수 있다
- 나중에 롤백, diff, publish 흐름으로 확장하기 쉽다

## 16. 왜 링크를 문자열로만 두지 않는가

### 기존 문제

문서 안의 링크를 단순 문자열로만 취급하면, 렌더링은 가능해도 구조적 탐색이 어렵다. 예를 들어 “이 문서를 가리키는 다른 문서 목록”을 구하려면 매번 모든 본문을 다시 파싱해야 한다.

### 등장한 개념

그래서 Websidian은 링크와 임베드를 **구조적 관계 데이터** 로 저장하는 방향을 잡는다. 

### Websidian에 대입

`document_links` 테이블은 source 문서, target 문서, relation type, raw target 을 저장하는 구조다. relation type은 `wikilink`, `markdown_link`, `embed_document`, `embed_html`, `external` 같은 값이 될 수 있다. 

### 왜 중요한가

이 구조가 있어야 나중에 다음 기능이 쉬워진다.

- 백링크
- 그래프 뷰
- 링크 무결성 검사
- 임베드 종류별 처리
- 외부 링크와 내부 링크 구분 

## 17. 왜 메타데이터와 바이너리를 분리하는가

### 기존 문제

DB에 모든 파일 원본을 직접 넣는 방식은 단순해 보일 수 있지만, 파일 용량이 커질수록 관리와 성능, 백업 전략이 복잡해진다. 반대로 파일 저장소만 쓰면 관계 조회와 메타데이터 관리가 약해진다.

### 등장한 개념

그래서 실제 시스템에서는 종종 **메타데이터는 DB**, **바이너리 원본은 객체 스토리지** 로 분리한다.

### Websidian에 대입

Websidian도 이 원칙을 따른다. `files` 테이블에는 object key, mime type, size, checksum 같은 메타데이터만 두고, 실제 파일 원본은 MinIO에 둔다. 

이 구조는 PostgreSQL과 MinIO를 각자 잘하는 일에 집중시키는 방식이다.

## 18. 지금 단계에서 꼭 잡아야 할 핵심 문장

아래 문장만 정확히 이해해도 DB 기초 감각은 많이 잡힌다.

- 데이터베이스는 단순 저장소가 아니라, 구조와 관계와 무결성을 관리하는 시스템이다. 
- 좋은 DB 설계는 SQL 문법보다 먼저 도메인 개념을 분명히 하는 데서 시작한다. 
- 관계형 데이터베이스는 테이블과 관계를 통해 중복을 줄이고 조회를 구조화한다. 
- 기본키와 외래키는 식별과 연결의 핵심 장치다. 
- 정규화는 데이터를 무작정 쪼개는 것이 아니라, 중복과 불일치를 줄이기 위한 사고방식이다. 
- Websidian에서는 문서와 파일을 구분하고, 링크와 버전을 구조적 데이터로 관리하는 것이 핵심이다.
