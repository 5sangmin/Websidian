# Git Workflow and AI Usage Rules

Websidian은 개인 프로젝트를 전제로 하지만, 가능한 구조적 개발 흐름을 경험하는 것을 목표로 한다.

이 문서는 아래 내용을 함께 정리한다.

- 개발 워크플로
- 브랜치 전략
- 배포 버전 관리 방식
- 커밋 / PR / 리뷰 규칙
- AI 사용 원칙

이 문서의 목적은 복잡한 개발 프로세스를 흉내 내는 것이 아니라, 개인 개발이더라도 구조적이고 다시 이어가기 쉬운 작업 흐름을 유지하는 것이다.

## 1. 기본 원칙

- `main`은 항상 배포 가능한 상태로 유지한다.
- `develop`은 개발 통합 브랜치로 사용한다.
- 모든 작업은 작은 단위로 나누고, 짧은 브랜치에서 진행한다.
- 코드와 문서는 같이 움직인다.
- AI는 적극 활용하되, 코드 작성의 주도권은 사람에게 둔다.
- 최종 판단, 최종 수정, 최종 머지는 항상 사람이 한다.

## 2. 브랜치 전략

현재 Websidian의 기본 브랜치 전략은 아래와 같다.

- `main`
  - 배포 브랜치
  - 홈랩 환경에 실제로 올릴 수 있는 안정 상태만 유지한다

- `develop`
  - 개발 통합 브랜치
  - 모든 작업 브랜치는 기본적으로 여기서 분기한다

- 작업 브랜치
  - `feat/...`
  - `fix/...`
  - `docs/...`
  - `chore/...`

브랜치 이름 예시:

- `feat/graph-view`
- `feat/tag-navigation`
- `fix/html-rendering`
- `docs/update-development-guide`
- `chore/compose-env-cleanup`

## 3. 작업 워크플로

기본 작업 순서는 아래와 같다.

1. 이슈를 작성한다.
2. 관련 문서를 읽는다.
3. 작업 범위를 가장 작은 단위로 나눈다.
4. `develop`에서 작업 브랜치를 생성한다.
5. 기능을 구현한다.
6. 작은 단위로 commit / push 를 반복한다.
7. PR을 생성한다. 대상 브랜치는 기본적으로 `develop`이다.
8. self-review 및 AI 리뷰를 수행한다.
9. 수정이 끝나면 PR을 머지한다.
10. 머지된 작업 브랜치는 삭제한다.
11. 관련 이슈를 종료한다.
12. `develop`이 배포 가능한 수준이 되면 `main`으로 머지하고 배포한다.

## 4. 머지 전략

### 작업 브랜치 -> develop

기본적으로 `Squash & Merge`를 사용한다.

이유:

- 작업 중간의 자잘한 커밋을 정리할 수 있다
- `develop` 히스토리를 기능 단위로 읽기 쉽게 유지할 수 있다
- self-review 이후 "이 작업은 결국 무엇을 추가/수정했는가"를 한 커밋으로 남길 수 있다

즉, 작업 브랜치 안에서는 자유롭게 여러 번 커밋하되, `develop`에는 정리된 결과만 남긴다.

### develop -> main

기본적으로 일반 merge를 사용한다.

이유:

- 배포 단위의 흐름을 남기기 쉽다
- `develop`에서 충분히 검증된 작업 묶음이 `main`으로 올라갔다는 이력이 보인다
- 나중에 어떤 시점에 어떤 배포가 나갔는지 추적하기 좋다

필요하면 상황에 따라 squash를 사용할 수 있지만, 기본값은 "배포 흐름이 보이도록 일반 merge"로 둔다.

### 머지 후 브랜치 정리

- 머지된 작업 브랜치는 삭제한다
- 로컬 브랜치와 원격 브랜치 모두 정리한다
- 오래된 브랜치를 남겨두지 않는다

## 5. 배포 버전 관리

Websidian은 배포 단위로 버전을 관리한다.

기본 버전 규칙은 Semantic Versioning 스타일을 느슨하게 따른다.

형식:

`MAJOR.MINOR.PATCH`

현재 프로젝트 단계에서는 아래 기준을 사용한다.

- `MAJOR`
  - 구조적 호환성 파괴나 큰 방향 전환이 있을 때
  - 예: 핵심 API 계약을 크게 바꾸는 경우

- `MINOR`
  - 새로운 기능 묶음이 배포될 때
  - 예: 그래프 뷰 추가, 태그 탐색 추가, 문서 버전 히스토리 추가

- `PATCH`
  - 기능 추가 없이 버그 수정, 안정화, 작은 개선만 있을 때
  - 예: 렌더링 버그 수정, 예외 처리 보완, 환경 변수 문제 수정

### 버전 운영 원칙

- 기능 하나를 완성했다고 바로 `main`에 올리지 않는다
- `develop`에서 여러 작업을 통합하고 확인한 뒤 배포 시점에 버전을 올린다
- "이번 배포에서 사용자 입장에서 무엇이 늘어났는가"를 기준으로 버전을 판단한다
- 버전은 작업 단위가 아니라 배포 단위에 붙인다

예시:

- `0.1.0` : 초기 실행 가능한 구조
- `0.2.0` : 그래프 뷰 추가
- `0.2.1` : 그래프 뷰 관련 버그 수정
- `0.3.0` : 태그 탐색 기능 추가

### 배포 절차

1. `develop`에서 배포 가능 상태를 확인한다
2. 버전을 결정한다
3. 필요하면 README 또는 변경 기록을 갱신한다
4. `develop`을 `main`으로 머지한다
5. `main` 기준으로 배포한다
6. Git tag를 남긴다
   - 예: `v0.2.0`

## 6. 커밋 규칙

커밋 메시지는 아래 형식을 기본으로 사용한다.

```text
type(scope): summary
```

예시:

- `feat(document): add document detail API`
- `feat(graph): add graph node response`
- `fix(embed): handle missing html target`
- `docs(readme): rewrite project overview`
- `chore(infra): add compose env example`

커밋 원칙:

- 한 커밋에는 한 목적만 담는다
- 커밋 제목만 읽어도 무엇이 바뀌었는지 보여야 한다
- 너무 큰 커밋을 만들지 않는다
- 작업 브랜치 안에서는 자잘한 커밋이 있어도 괜찮지만, PR 머지 전에는 전체 흐름이 읽혀야 한다

## 7. PR 규칙

PR은 협업 절차이면서 동시에 solo 개발에서의 self-review 도구로 사용한다.

기본 원칙:

- 모든 의미 있는 작업은 PR을 거친다
- PR의 base branch는 기본적으로 `develop`이다
- 배포 PR만 `main`을 대상으로 한다

PR에는 아래 내용을 포함한다.

- 변경 목적
- 주요 변경 사항
- 직접 확인한 내용
- 문서 반영 여부
- 관련 이슈

PR 제목은 가능한 한 작업 결과가 드러나게 작성한다.

예시:

- `feat(graph): add basic graph view`
- `fix(document): handle missing current version`
- `docs(development): add git workflow guide`

## 8. Self-review 규칙

개인 개발이더라도 PR 머지 전에는 반드시 self-review를 수행한다.

최소 확인 항목:

- 관련 없는 변경이 섞이지 않았는가
- 디버그 코드가 남아 있지 않은가
- 이름이 이상하지 않은가
- 예외 처리가 빠지지 않았는가
- 실행 확인을 했는가
- 문서 갱신이 필요한데 빠뜨리지 않았는가

개인 개발에서는 self-review가 사실상 코드 리뷰의 핵심이다.

## 9. AI 사용 원칙

Websidian에서 AI는 적극적으로 사용한다.
하지만 AI는 "대신 개발해 주는 주체"가 아니라, 설계/문서/리뷰/정리의 강한 보조 도구로 사용한다.

핵심 원칙은 아래와 같다.

- AI는 적극 활용한다
- 그러나 코드 작성의 주도권은 사람에게 둔다
- 최종 구현과 최종 수정은 직접 한다
- AI 출력은 항상 검토 후 반영한다
- 문서와 현재 구조를 기준으로 AI를 사용한다

### AI를 주로 사용하는 영역

- 설계 검토
- 문서 초안 작성
- 커밋 메시지 정리
- PR 제목 / 본문 초안 작성
- 리뷰 포인트 정리
- 리팩토링 후보 검토
- 누락된 예외 처리나 테스트 관점 점검

### AI에게 주도권을 주지 않는 영역

- 저장소 전체 구조를 AI가 임의로 결정하도록 맡기지 않는다
- 문서와 충돌하는 구조를 AI 제안만으로 채택하지 않는다
- 생성된 코드를 검토 없이 그대로 커밋하지 않는다
- 실행 확인 없이 AI 결과를 신뢰하지 않는다

## 10. AI 사용 방식

### 질문 -> 피드백 -> 구현

기본 루프는 아래와 같다.

1. 문제를 한 줄로 정리한다
2. 관련 문서를 읽는다
3. AI에게 설계/구조/구현 방향을 질문한다
4. 피드백을 바탕으로 직접 구현한다
5. 구현 결과를 다시 AI와 함께 검토한다
6. 직접 수정 후 PR을 만든다

즉, AI는 방향 제시와 검토에 적극 활용하되, 실제 개발은 사람이 수행한다.

### 문서 기반 질문

AI에게 요청할 때는 가능한 한 아래를 함께 준다.

- 현재 작업 목표
- 관련 문서 경로
- 현재 구조상의 제약
- 이번 작업에서 일부러 하지 않을 범위

예시:

- `docs/backend/module-structure.md` 기준으로 Document API 초안을 검토해줘
- `docs/database/schema-draft.md`와 충돌하지 않게 version 테이블 변경안을 봐줘
- 이번 작업은 graph view API 응답까지만 하고 렌더링은 제외할 거야

## 11. AI 코드 리뷰 사용 원칙

AI 코드 리뷰는 도입한다.
다만 목적은 "자동으로 정답을 얻기"가 아니라, 사람이 놓친 부분을 추가로 점검하는 것이다.

기본 원칙:

- AI 리뷰는 보조 수단이다
- 최종 approve는 사람이 한다
- AI 리뷰 코멘트는 모두 수용하지 않는다
- 구조, 네이밍, 예외 처리, 테스트 관점 중심으로 참고한다

권장 흐름:

1. PR 생성
2. self-review 수행
3. AI 리뷰 실행 또는 diff 기반 질문
4. 반영할 항목과 무시할 항목을 구분
5. 직접 수정
6. 머지

## 12. 문서 반영 규칙

아래가 바뀌면 문서를 같이 확인한다.

- 도메인 개념
- API 구조
- DB 스키마
- 환경 변수
- 실행 절차
- 개발 워크플로
- 배포 방식
- 브랜치 전략
- AI 사용 방식

즉, 코드만 바꾸고 문서를 방치하지 않는다.

## 13. 하지 않을 것

아래는 가능한 한 피한다.

- 큰 기능을 문서 없이 바로 구현 시작
- `main`에서 직접 오래 작업하기
- 기능 추가와 구조 리팩토링을 한 번에 섞기
- AI가 제안한 코드를 검토 없이 반영하기
- 문서가 틀린 걸 알면서 그대로 두기
- 지금 필요 없는 복잡한 확장성을 먼저 만들기

## 14. 최종 운영 원칙

Websidian의 Git / PR / 배포 / AI 사용 원칙은 아래 한 문장으로 요약한다.

작업은 작게 나누고, 브랜치는 명확히 분리하고, 배포는 버전으로 남기고, AI는 적극 활용하되 개발의 최종 주도권은 사람에게 둔다.
