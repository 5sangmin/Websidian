# Development Guide

## Purpose

이 문서는 Websidian을 개발할 때 어떤 순서로 작업하고, 무엇을 문서화하고, 어떤 기준으로 코드를 수정할지 정리한 개인 개발 가이드다.

이 문서의 목적은 팀 협업 절차를 정의하는 것이 아니다.
목적은 작업 흐름이 흔들리지 않게 하고, 시간이 지난 뒤에도 다시 프로젝트를 쉽게 이어갈 수 있도록 하는 것이다.

즉, 이 문서는 개발의 최소 규약 문서다.

## Core principle

Websidian 개발의 기본 원칙은 아래와 같다.

1. 큰 기능을 한 번에 만들지 않는다.
2. 설계와 구현의 경계를 먼저 이해한다.
3. 미래의 내가 잊을 내용을 문서로 남긴다.
4. 코드와 문서가 어긋나면 바로 정리한다.
5. 실행해 보고 확인한 뒤 다음 단계로 간다.

핵심은 속도보다 지속 가능성이다.
개발할 때 가장 위험한 것은 느림이 아니라, 문맥을 잃고 프로젝트를 다시 못 이어가는 것이다.

## Daily workflow

기본 작업 흐름은 아래와 같다.

1. 아이디어, 문제, 버그를 적는다.
2. 관련 문서를 읽는다.
3. 이번 작업 범위를 작게 정한다.
4. 필요하면 문서를 먼저 갱신한다.
5. 구현한다.
6. 직접 실행해서 확인한다.
7. 필요한 문서를 갱신한다.
8. 다음 작업 메모를 남긴다.

## Before starting work

작업을 시작하기 전에 아래를 먼저 확인한다.

### 1. 무엇을 하려는지 한 줄로 적기

예:
- Vault 대표 문서 지정 API 추가
- Markdown embed parsing 수정
- Compose 환경 변수 구조 정리

한 줄 설명이 안 되면 작업 범위가 너무 크거나 모호한 경우가 많다.

### 2. 관련 문서 읽기

작업 전에 아래를 확인한다.

- 제품 목적과 맞는가
- MVP 범위 안인가
- 기존 구조와 충돌하지 않는가
- 이미 문서로 결정된 내용이 있는가

기본 읽기 기준:

- 제품 방향: `docs/vision/*`
- 구조/개념: `docs/architecture/*`
- DB 변경: `docs/database/*`
- API 변경: `docs/backend/*`
- 프론트 구조: `docs/frontend/*`
- 인프라/실행: `docs/infra/*`, `docs/operations/*`

추가로 개인적인 학습 내용은 `docs/learning/*`,  
진행 중 작업 메모와 세션 기록은 `docs/working/*`에 정리한다.

### 3. 작업 범위 줄이기

한 번에 너무 많이 하지 않는다.

좋은 예:
- 문서 단건 조회 API만 구현
- HTML 문서 타입만 먼저 지원
- env 변수 이름 정리만 수행

나쁜 예:
- 문서 시스템 전체 구현
- frontend/backend/db/infra를 한 번에 전부 개편
- 검색/버전/권한을 동시에 시작

## When to write docs first

모든 작업을 문서부터 시작할 필요는 없다.
하지만 아래 경우에는 문서를 먼저 정리하는 것이 좋다.

- 새로운 개념을 도입할 때
- 여러 계층에 영향을 줄 때
- 구조를 바꿀 때
- 나중에 왜 이렇게 했는지 잊기 쉬울 때
- 데이터 모델을 바꿀 때
- API 계약을 바꿀 때

예:
- HTML 문서를 1급 문서로 다루는 방식
- entry document 구조 변경
- 권한 모델 초안 변경
- compose 서비스 구조 변경

## When to code first

아래 경우에는 바로 구현부터 시작해도 된다.

- 작은 버그 수정
- 명확한 범위의 UI 수정
- 테스트 추가
- 이미 문서 방향이 정해진 기능의 작은 하위 작업
- 오타, 경로, 이름 같은 소규모 수정

원칙은 간단하다.

- 결정이 필요한 작업은 문서를 먼저
- 실행만 남은 작업은 바로 구현

## Recommended work unit

개발할 때는 작업 단위를 작게 유지해야 한다.
권장 단위는 아래 정도다.

- 한 API 엔드포인트
- 한 화면의 한 기능
- 한 도메인 규칙
- 한 문서 파일의 명확한 갱신
- 한 compose 서비스 추가 또는 수정
- 한 migration 단위의 스키마 변경

작업 단위가 작아야 다시 보기 쉽고, 중간에 멈춰도 이어가기 쉽다.

## Personal work sequence

실제 작업은 아래 순서를 기본값으로 둔다.

### 1. Capture

먼저 떠오른 생각을 놓치지 않는다.

적을 대상:
- 새 기능 아이디어
- 버그
- 나중에 개선할 점
- 설계 의문점

형식은 자유롭다.
중요한 것은 머릿속에만 두지 않는 것이다.

### 2. Clarify

이 작업이 실제로 지금 해야 할 일인지 정리한다.

체크:
- MVP 범위 안인가
- 지금 막고 있는 문제인가
- 다른 선행 작업이 필요한가
- 나중으로 미뤄도 되는가

### 3. Read

관련 문서를 읽고 현재 구조를 확인한다.

### 4. Slice

작업을 가장 작은 실행 단위로 쪼갠다.

예:
문서 기능 구현 대신
- 문서 엔티티 정의
- 문서 단건 조회
- Markdown 응답
- HTML 응답
- 링크 응답

처럼 나눈다.

### 5. Build

작게 구현한다.

### 6. Verify

직접 실행해서 확인한다.

최소 확인:
- 앱이 뜨는가
- API가 응답하는가
- 문서가 렌더링되는가
- 환경 변수 누락은 없는가
- DB/MinIO 연결이 되는가

### 7. Record

필요한 문서를 갱신한다.

### 8. Leave a clean next step

작업이 끝나면 다음에 이어서 할 수 있도록 메모를 남긴다.

예:
- 다음 작업 후보
- 남은 문제
- 이번에 일부러 안 한 것
- 다음에 읽어야 할 문서

## Git usage

개인 개발이더라도 Git 사용 원칙은 단순하게 유지한다.

실제 Git 운영 규칙과 배포/AI 사용 기준은 [`git-workflow-and-ai-usage-rules.md`](./git-workflow-and-ai-usage-rules.md)에서 관리한다.  
반복해서 사용하는 작업 초안은 `templates/` 디렉토리에 따로 정리하며, 이슈, PR, 커밋, 릴리즈, 작업 메모 템플릿은 필요할 때 복사해서 사용한다.

이 문서에서는 Git의 상세 규칙을 모두 반복하지 않고, development guide의 흐름과 직접 연결되는 최소 원칙만 유지한다.

### Minimal Git principle

- `main`은 가능한 한 다시 시작 가능한 상태로 유지한다.
- 큰 작업은 바로 `main`에서 하지 않는다.
- 기능/수정 단위 작업은 짧은 브랜치로 만든다.
- 커밋은 읽히는 기록으로 남긴다.
- 머지 전에는 반드시 한 번 멈춰서 diff와 실행 결과를 확인한다.

## Rules for development

### Rule 1. main을 항상 다시 시작 가능한 상태로 유지한다

개인 개발이더라도 main은 가능한 한 깨끗하게 유지한다.
너무 큰 미완성 변경을 오래 끌지 않는다.

### Rule 2. 기능 추가와 구조 정리를 가능한 분리한다

예:
- 새 API 추가
- 폴더 구조 리팩토링

이 둘은 가능하면 동시에 하지 않는다.

### Rule 3. 문서와 코드는 같이 움직인다

아래가 바뀌면 문서도 확인한다.

- 도메인 개념
- API 구조
- DB 스키마
- 환경 변수
- 실행 절차

### Rule 4. 한 번에 한 문제만 푼다

개발할 때 가장 흔한 실수는 한 작업을 하다가 다른 문제까지 계속 파고드는 것이다.
작업 중 새 문제가 보이면 바로 해결하지 말고 메모만 남긴다.

### Rule 5. 나중의 나를 위한 흔적을 남긴다

문서, 주석, 짧은 메모, TODO 모두 좋다.
단, 왜 이렇게 했는지가 남아야 한다.

## File and document discipline

문서와 파일은 아래 기준으로 유지한다.

### README

README는 프로젝트 입구다.
다음을 빠르게 이해할 수 있어야 한다.

- 이 프로젝트가 무엇인지
- 왜 존재하는지
- 지금 어디까지 왔는지
- 어디부터 읽으면 되는지

### Vision docs

방향이 흔들릴 때 돌아오는 기준점이다.

### Architecture docs

구조와 경계를 설명한다.
코드가 커질수록 더 중요해진다.

### Database docs

데이터를 바꾸기 전에 먼저 확인하는 문서다.

### Infra/Operations docs

시간이 지나 가장 다시 보기 어려운 부분이다.
그래서 꼭 유지한다.

### Development docs

개발 흐름을 잃었을 때, 길을 찾기 위한 문서로 유지한다.

## Coding discipline

### 이름을 대충 짓지 않는다

변수, 함수, 클래스, 문서 이름은 역할이 드러나야 한다.

### 책임을 섞지 않는다

controller, service, repository, component, composable, schema 책임을 섞지 않는다.

### 작동만 하지 말고 읽히게 만든다

개인 개발이라도 결국 가장 자주 코드를 읽는 사람은 나다.

### 예외를 무시하지 않는다

성공 케이스만 처리하지 않는다.
없을 수 있는 값, 실패할 수 있는 요청, 깨질 수 있는 파일을 고려한다.

### 하드코딩을 남발하지 않는다

환경 변수, 경로, bucket 이름, 포트 등은 문서화 가능한 형태로 분리한다.

## Verification checklist

작업 후에는 최소한 아래를 확인한다.

### 공통
- 변경 목적이 실제로 반영되었는가
- 관련 없는 것이 같이 바뀌지 않았는가
- 문서를 갱신해야 하는데 빠뜨리지 않았는가

### Backend
- 앱 기동 가능
- health 확인 가능
- API 응답 확인 가능
- DB 연결 문제 없음
- MinIO 연결 문제 없음

### Frontend
- 화면 접근 가능
- 브라우저 콘솔 오류 없음
- API 연동 확인
- 기본 라우팅 확인

### Infra
- Compose 기동 가능
- 환경 변수 누락 없음
- 볼륨/포트 충돌 없음

## What not to do

아래는 가능한 피한다.

- 기능 범위가 큰데 바로 구현부터 시작
- 문서와 다른 구조를 그냥 밀어붙이기
- 실행 확인 없이 아마 될 것이라고 넘어가기
- 하다 보니 나온 다른 문제까지 한 번에 해결하려고 하기
- 문서가 오래된 걸 알면서 그대로 두기
- 지금 필요 없는 복잡한 확장성까지 먼저 만들기

## Recommended rhythm

개발할 때는 아래 리듬이 좋다.

1. 작게 계획
2. 작게 구현
3. 바로 실행
4. 바로 수정
5. 바로 기록

이 리듬이 길게 보면 가장 빠르다.

## If stuck

막히면 아래 순서를 따른다.

1. 문제를 한 줄로 다시 적는다
2. 관련 문서를 다시 읽는다
3. 범위를 더 줄인다
4. 최소 재현 케이스를 만든다
5. 지금 풀지 않아도 되는 부분을 분리한다
6. 필요한 경우 결정 사항을 문서로 먼저 적는다

## Final principle

Websidian을 개발할 때의 핵심 원칙은 아래와 같다.

**작게 나누고, 직접 확인하고, 잊을 것만 문서로 남긴다.**
