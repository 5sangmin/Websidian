## Starting context

- 같은 날짜의 이전 세션에서 Flyway V1 migration을 적용해 `vaults`, `documents`, `document_versions` 스키마를 확정한 상태였다.
- DB 레벨의 테이블/제약 조건은 준비되었지만, 아직 JPA 엔티티와 repository 계층은 실제 코드로 고정되지 않은 상태였다.
- 특히 `documents(vault_id, slug)`와 `document_versions(document_id, version_no)`의 unique 제약이 실제 persistence 테스트에서 어떻게 보이는지 확인이 필요했다.
- entry document는 Published 문서만 가능하다는 도메인 규칙도 엔티티 레벨과 persistence 테스트 양쪽에서 확인하고 싶었다.

## What I did

- `backend/src/main/java/com/websidian/document/domain/` 아래에 `Vault`, `Document`, `DocumentVersion` 엔티티와 enum/converter들을 정리했다.
- 각 엔티티에 V1 스키마 기준의 unique constraint, soft delete, 양방향 관계를 반영했다.
  - `Vault`: `slug` unique, `entryDocument`, `documents`
  - `Document`: `(vault_id, slug)` unique, `currentVersion`, `versions`, `status`
  - `DocumentVersion`: `(document_id, version_no)` unique
- `@SQLDelete`, `@SQLRestriction`을 사용해 `Vault`, `Document`에 soft delete 패턴을 적용했다.
- `Document.publish()`, `Vault.changeEntryDocument()` 같은 도메인 규칙 메서드를 추가해 Published 문서만 entry document로 지정되도록 했다.
- domain port 역할의 `DocumentRepository`, `DocumentVersionRepository`, `VaultRepository` 인터페이스를 정의했다.
- `JpaDocumentRepository`, `JpaDocumentVersionRepository`, `JpaVaultRepository`를 Spring Data JPA 기반 persistence adapter로 작성했다.
- `DocumentPersistenceTest`를 작성/보강해 다음 시나리오를 검증했다.
  - Vault / Document / DocumentVersion 저장 및 재조회
  - 최신 `version_no` 조회
  - Published 문서만 entry document 지정 가능
  - 같은 Vault 내 duplicate slug 저장 실패
  - 같은 Document 내 duplicate `version_no` 저장 실패
- 테스트 중 `findById` 호출이 domain port와 `CrudRepository` 사이에서 모호해지는 문제를 확인했고, 테스트에서는 `findBySlug`를 사용해 우선 회피했다.
- `./gradlew test --tests "com.websidian.document.infrastructure.persistence.DocumentPersistenceTest" --info` 실행으로 전체 5개 테스트 GREEN을 확인했다.

## Decisions

- 이번 단계에서는 application service나 controller보다 **persistence layer first cut** 완성에 집중한다.
- repository는 당장은 **domain port + Spring Data interface 직접 결합** 방식으로 간단히 유지한다.
- 다만 `findById(UUID)`를 domain port에 다시 선언하면 Spring Data 기본 메서드와 충돌할 수 있으므로, 이 부분은 후속 정리 대상으로 남긴다.
- unique constraint 보장은 application 레벨 선검사만 믿지 않고 **DB 제약 + persistence test**로 고정한다.
- entry document 규칙은 "Published 문서만 가능"을 엔티티 메서드에서 먼저 강제한다.

## Problems / blockers

- `VaultRepository`, `DocumentRepository`, `DocumentVersionRepository`의 `findById(UUID)` 선언이 Spring Data `CrudRepository#findById`와 겹쳐 테스트 코드에서 모호성 문제가 발생했다.
- 현재는 테스트에서 `findBySlug`를 사용해 우선 회피했지만, repository port 설계는 후속 세션에서 한 번 정리할 필요가 있다.
- soft delete 필터링 자체는 엔티티 어노테이션으로 반영했지만, 삭제 시나리오에 대한 persistence 테스트는 아직 작성하지 않았다.

## Out of scope discovered

- `CreateDocumentService`, `PublishDocumentService` 같은 application layer 유스케이스 구현은 이번 세션 범위에서 제외했다.
- REST API (`DocumentController`, DTO, request/response`)는 아직 시작하지 않았다.
- `docs/operations/dev-environment.md`와 같은 운영 문서는 이번 세션 변경사항과 직접 연결되지 않아 수정하지 않았다.
- soft delete 동작, 복구 시나리오, deleted row 조회 정책 테스트는 후속 작업으로 미뤘다.
