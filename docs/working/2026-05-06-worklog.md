## Starting context

- Websidian 문서 구조는 전반적으로 준비되어 있으나, 실제 개발 워크플로(이슈 → 브랜치 → 커밋 → 워크로그) 첫 적용은 아직 시작 전인 상태였다.
- 어떤 단위부터 구현을 시작할지 (Vault vs Document, DB vs Backend vs Frontend, 수평 vs 수직 개발) 감이 애매했음.
- Docker/Compose 기반 개발 환경과 홈랩 Proxmox + Ubuntu VM, Windows 데스크탑을 함께 쓰는 구조를 어떻게 맞출지 방향만 정해진 상태였다.

## What I did

- Space 지침/문서를 바탕으로 Websidian의 전체 문서 구조와 개발 원칙을 다시 정리했다.
- 개발 단위는 “수평(전체 DB → 전체 backend → 전체 frontend)”이 아니라 “도메인 모듈 단위의 수직 개발”로 가져가기로 재확인했다.
- 첫 기능 단위를 Vault가 아니라 Document 모듈로 잡고, `feat(document): basic document and version persistence` 이슈를 첫 작업으로 진행하기로 결정했다.
- 이 이슈 안에서는 DB 마이그레이션 + JPA 리포지토리 + 테스트까지만 포함하고, API/프론트는 후속 이슈로 분리하기로 범위를 정했다.
- Websidian용 이슈 초안을 `issue-template.md` 형식에 맞춰 작성했다.
- 루트 `.gitignore`를 Websidian monorepo(backend/frontend/infra/db) 구조에 맞게 설계했고, 바로 커밋 가능한 완성본을 만들었다.

## Decisions

- 첫 개발 이슈는 `feat(document): basic document and version persistence`로 하고, 작업 브랜치는 `feat/document-basic-persistence`로 사용한다.
- Document 모듈 이슈의 첫 깊이는 “DB + 리포지토리 + 테스트(infrastructure layer 중심)”까지만로 제한하고, service/controller/API는 별도 이슈로 나눈다.
- 두 개발 PC(Windows 데스크탑, 홈랩 Ubuntu VM)는 모두 Docker + Compose를 공통 기반으로 쓰며, 같은 `infra/compose/compose.dev.yml` + `.env.example` 구조를 공유한다.
- `.gitignore`로 Node/Gradle 산출물, 로그, env 파일, 에디터 설정 등을 초기에 차단해, 두 환경 모두에서 깨끗한 Git 상태를 유지한다.
