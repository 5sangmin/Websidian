## What I Did

### 1. Flyway 도입 결정

- DB 스키마 변경 이력을 코드와 함께 관리하기 위해 Flyway 선택
- Liquibase 대신 Flyway를 선택한 이유:
  - SQL 기반 마이그레이션이 더 직관적 (XML/YAML 불필요)
  - Spring Boot와의 통합이 간단 (`spring-boot-starter-flyway`)
  - 혼자 개발하는 프로젝트에서 Liquibase의 rollback 기능은 오버엔지니어링
- `backend/build.gradle`에 Flyway 의존성 추가 (이미 완료된 상태였음)
- `backend/src/main/resources/application.properties`에 Flyway 설정 완료:
  - `spring.flyway.enabled=true`
  - `spring.flyway.locations=classpath:db/migration`
  - `spring.flyway.baseline-on-migrate=true`
  - `spring.jpa.hibernate.ddl-auto=validate` (Flyway가 스키마 관리, JPA는 검증만)

### 2. V1 Migration SQL 작성

- `backend/src/main/resources/db/migration/V1__create_core_document_schema.sql` 생성
- Vault, Document, DocumentVersion 테이블 정의
- 주요 결정 사항:
  - **UUID PK**: 분산 확장성 + MinIO 연동 용이성
  - **Soft delete**: `deleted_at TIMESTAMPTZ NULL`로 복구 가능한 삭제 구현
  - **순환 FK**: documents ↔ document_versions 상호 참조를 Deferred FK로 해결
  - **content_snapshot**: V1에서는 DB TEXT로 저장, V2에서 MinIO 이관 검토
  - **CHECK 제약**: document_type, status, visibility 같은 enum 값 DB 레벨에서 제한
  - **Partial Index**: `WHERE deleted_at IS NULL` 조건으로 활성 데이터만 인덱싱
  - **Trigger**: `updated_at` 자동 갱신 (vaults, documents)
- 테이블별 COMMENT 추가로 스키마 의도 문서화
- 인덱스 설계:
  - `idx_vaults_slug`: Vault slug 조회 최적화
  - `idx_documents_vault_slug`: Vault 내 문서 slug 조회 최적화
  - `idx_documents_vault_status`: 활성 문서 필터링 최적화 (Partial Index)
  - `idx_document_versions_document_version`: 최신 버전 조회 최적화 (DESC)
  - `idx_vaults_active`, `idx_documents_active`: soft delete 필터링 최적화

## Decisions Made

### Flyway vs Liquibase

- Flyway 선택
- 이유: SQL 기반 마이그레이션이 직관적, Spring Boot 통합 간단, rollback 불필요 (혼자 개발)

### Multi-stage Dockerfile 도입

- 기존: 호스트에서 빌드한 JAR를 컨테이너에 마운트
- 변경: Dockerfile 내부에서 빌드 + 실행 환경 분리
- 이유:
  - 호스트 의존성 제거 (Gradle/Java 설치 불필요)
  - 프로덕션 배포 가능한 구조
  - 재현성 보장 (로컬 환경 차이 제거)

### V1 스키마 범위

- 포함: Vault, Document, DocumentVersion
- 제외: users, files, document_links, tags, permissions
- 이유: persistence 레이어 first cut에 집중, 나머지는 V2+ 단계적 추가

### content_snapshot 저장 위치

- V1: DB의 TEXT 컬럼에 저장
- 이유: 구현 단순화, 트랜잭션 보장
- V2 검토: MinIO 이관 (대용량 문서 효율성)

### Soft delete 구현

- `deleted_at TIMESTAMPTZ NULL` 패턴 사용
- 이유: 복구 가능, 감사 추적, FK 참조 보호

### JPA ddl-auto 설정

- `validate` 선택 (기존 `none`, `create`, `update` 대신)
- 이유:
  - Flyway가 스키마 관리하므로 JPA의 DDL 자동 생성 불필요
  - `validate`로 엔티티-스키마 일치 여부 검증 (불일치 시 startup 실패)
  - 마이그레이션 누락 방지

- vaults 테이블:
  - PK: id (UUID)
  - UNIQUE: slug
  - FK: entry_document_id → documents(id) ON DELETE SET NULL
  - CHECK: visibility IN ('public', 'private')
  - Soft delete: deleted_at TIMESTAMPTZ NULL
  - Trigger: updated_at 자동 갱신
- documents 테이블:
  - PK: id (UUID)
  - FK: vault_id → vaults(id) ON DELETE CASCADE
  - FK: current_version_id → document_versions(id) ON DELETE SET NULL
  - UNIQUE: (vault_id, slug)
  - CHECK: document_type IN ('markdown', 'html')
  - CHECK: status IN ('draft', 'published', 'archived')
  - Soft delete: deleted_at TIMESTAMPTZ NULL
  - Trigger: updated_at 자동 갱신
- document_versions 테이블:
  - PK: id (UUID)
  - FK: document_id → documents(id) ON DELETE CASCADE
  - UNIQUE: (document_id, version_no)
  - CHECK: source_type IN ('markdown', 'html')
  - CHECK: version_no > 0
  - Immutable: created_at만 존재, updated_at 없음
